An erasure deletes a first load's object on a segment with no generation yet, after renewing the row's `pointerId` so the load that wrote it is refused at its publish, and reports `erased: true`; an object sealed under a key no row holds is deleted whatever the id, so on an encrypted store an erasure of any id refuses an encrypted first load in flight that has written its object onto a segment made ahead of its data. The fence before deleting a generation above the pointer is the same renewal, and a renewal that gets no answer is settled by reading the row. On an encrypted segment, an object sealed under a key its row does not hold is deleted as a holder the erasure cannot search, where every erasure threw an AEAD `IntegrityError`. Each of these deletes by name passes the version of the read that made the object a holder, so on a storage driver that reports `conditionalDelete` a load that took the number since keeps its generation. An erasure that meets another object's bytes under a number it was searching takes the object it listed for gone, where it threw `IntegrityError`. A refused rewrite that discards its own object above the winner's pointer proves it its own by a read of its footer first and deletes it under that read's version, so a load that took the number since keeps its generation there too.
