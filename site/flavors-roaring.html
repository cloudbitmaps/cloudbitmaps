Flavors / Roaring

@cloudbitmaps/roaring Shipped 0.4.1 Apache-2.0 OIDC + SLSA

Sparse or clustered ids, compressed by containers that pick themselves.

The Roaring format splits a 32-bit id into a 16-bit chunk key and a 16-bit remainder, then stores each chunk in whichever representation is smallest — a sorted array, a dense bitset, or a run-length list. It is the right default for id spaces with holes in them, which is most of them.

Take this flavor when
  • Ids are sparse or clustered — user ids, event ids, anything with gaps.
  • You want the strongest compression per chunk without tuning anything.
  • You are moving off Redis sets and want the closest thing to a drop-in.
Take something else when
  • You need sub-millisecond p99 on a bounded working set — that is Redis, not this library, and not any flavor of it.
  • You cannot take a native dependency — wait for @cloudbitmaps/bitmap.
  • Your ids are dense and contiguous; adaptive containers buy you nothing there.
Codec

How a chunk picks its representation

This is the only animation on a flavor page, and it explains only the codec — the tiering and chunk-skipping story lives once, on /architecture, because it is codec-independent. A second flavor drops its own version into this slot and changes nothing else.

Encode · write path 12s loop · 4 stages
01 Split 1,234,567,890 → key 0x4996 rem 0x02D2 16 bits + 16 bits
02 Group 0x0000 · 2 ids 0x0001 · 61,904 ids 0x4996 · 9,001 ids one chunk = 2¹⁶ ids
03 Choose array 18 KiB — 2 B × 9,001 bitset 8 KiB — flat, always ← winner run 24 KiB — 4 B × 6,102 runs smallest encoding wins,
per chunk, on write
04 Store ARR BITSET RUN ARR one segment,
mixed containers

No configuration, no hint, no tuning knob — the container is decided per chunk by whichever encoding measures smallest. A real segment routinely holds all three at once, and the chunk key above the payload is what lets two segments intersect without downloading either.

Id split

id < 2³² → chunkKey 16-bit
remainder 16-bit

Why it matters here

The chunk key is what makes intersection cheap across tiers: two segments only exchange chunks whose keys appear in both. The codec decides the bytes inside a chunk; the key alignment is the engine's.

Usage

Zero setup: in-memory in six lines

A store is wired to a warm driver for live mutations and a cold source for the immutable archive. The in-memory drivers need no setup — swap in the S3 and DynamoDB drivers later and the code above them does not change.

quickstart.tsSame API in production 
import { CloudRoaring, MemoryWarmDriver, MemoryColdChunkSource } from '@cloudbitmaps/roaring';

const store = new CloudRoaring({
  warm: new MemoryWarmDriver(),
  cold: new MemoryColdChunkSource(),
});

const vips = store.segment('high-value-shoppers');
await vips.addMany([75, 99_999, 1_234_567_890]); // grouped by chunk
await vips.has(1_234_567_890);                    // true
await vips.count();                                // exact cardinality, 0 payload reads

What these numbers do not establish

Published on every page that quotes a figure, in the same panel as the figure.

  1. Published rates × wire-metered ops — not a cloud bill. Request tiers and storage-class transitions are unmeasured; Cost Explorer reconciliation is blocked on the account.
  2. Cost, not latency. Wall-clock throughput is too noisy to gate on shared CI runners. The one latency claim we make is scoped: a 2026-07-27 in-region run puts a warm has() at p50 5.27 ms / p99 12.71 ms (n=2,000) — “p99 inside budget”, not “always”.
  3. Your region and workload move the crossover. Feed your own PricingProfile into the shipped estimateCost() — the same function the chart is generated from, so the page cannot drift ahead of the library.
  4. It is pre-1.0 and single-maintainer. The real risk is operational maturity, not losing the bytes — they are immutable, documented, and in your bucket. exportSegments() is a one-command exit.
