Six lines, then the same six lines

The only difference between these two is which drivers the constructor is handed. Nothing above it knows, or can know, which tier it is talking to.

quickstart.tsNo setup 
import {
  CloudRoaring, MemoryWarmDriver, MemoryColdChunkSource,
} from '@cloudbitmaps/roaring';

const store = new CloudRoaring({
  warm: new MemoryWarmDriver(),
  cold: new MemoryColdChunkSource(),
});

const vips = store.segment('high-value-shoppers');
await vips.addMany([75, 99_999, 1_234_567_890]);
await vips.has(1_234_567_890);  // true
await vips.count();            // exact, 0 payloads
production.tsOnly the constructor 
import { CloudRoaring } from '@cloudbitmaps/roaring';
import { S3ColdDriver } from '@cloudbitmaps/roaring/s3';
import { DynamoDbWarmDriver }
  from '@cloudbitmaps/roaring/dynamodb';

const store = new CloudRoaring({
  warm: new DynamoDbWarmDriver({ client, table: 'deltas' }),
  cold: new S3ColdDriver({ client, bucket: 'segments' }),
  hot: { maxChunks: 512 },   // optional bounded LRU
});

// …every line below here is unchanged

The hot tier is optional in the strict sense: leave it out and everything still returns the same answers, just with more warm round trips.

The whole API

Deliberately the shape of an in-memory Set. What is new is where the bytes live, not what you call — so the third column, which tiers a call touches, is the one worth reading.

Segment and storeScrolls sideways on narrow screens
Call Does Touches
add(id) · addMany(ids) Appends to the chunk's delta row. Ids are grouped by chunk first, so a bulk add is one write per chunk, not per id. warm
has(id) Resolves one chunk: hot if it is cached, otherwise the cold payload merged with the warm deltas. hot → warm + cold
remove(id) · removeMany(ids) Records a tombstone in the delta row. Cold objects are never mutated in place, so a delete is a small write rather than a rebuild. warm
count() Sums per-chunk cardinality from metadata. Exact, not estimated — no HyperLogLog — and it never opens a payload. metadata only
intersect(others) Async-iterates the intersection. Compares chunk keys first and fetches only shared chunks; the cold payload footprint is bounded by concurrency × operands × chunk. Warm is a separate term outside that window — each operand's rows are snapshotted up front, so budget operands × maxWarmScanBytes as well. shared chunks only
compactSegment()
runCompactionCycle() 		Folds deltas into a new immutable cold generation and drops the rows. Schedule it; do not call it per write. cold
store.exportSegments(sink) Writes every registered segment out as cross-language roaring or newline-delimited ndjson, using only public read APIs. The one-command exit, and there is a CLI that wraps it. cold
estimateCost(profile) Your region and rates in, projected bill out. The benchmarks page is generated from this same function. nothing — pure

The API reference is checked against the real exports by CI, so it cannot drift from the package.

Ten drivers, two independent choices

Warm and cold are picked separately. Anything with a cheap range read works as cold; anything with cheap small writes works as warm. Each backend's SDK is an optional peer — install only the ones you use.

Redis is in this table, and choosing it is a real answer to the write crossover: a flat node you already run has no per-request meter to cross. It is a warm driver, so it holds recent chunk deltas while the corpus stays in cold object storage — which is a much smaller node than one sized to keep your whole history in RAM.

Memory drivers ship in the main entry too and need nothing — they are what the quickstart uses. An S3-compatible endpoint (R2, MinIO) works through the S3 driver by pointing the client's endpoint at it.

Estimate your own bill

Our published numbers are us-east-1 on-demand. Yours are not. Feed your own rates in and get your own crossover — and the site cannot drift ahead of the library, because both call this function.

estimate.tsPure — touches nothing 
import { estimateCost, AWS_US_EAST_1_ONDEMAND }
  from '@cloudbitmaps/roaring';

const bill = estimateCost({
  writesPerSec: 40,
  readsPerSec: 800,
  pricing: myPricingProfile,  // or the AWS default
});
  • 01 Schedule the compaction cycle deltas are not free Warm rows accumulate until something folds them into a new cold generation. Nothing does that on its own.
  • 02 Bound the hot cache to what your runtime can hold maxChunks It is an LRU with a hard ceiling, and the ceiling is yours to choose. Correctness does not depend on it either way.
  • 03 Keep one old generation for snapshots $0.03/mo · 1.2 GiB Cold objects are immutable and generation-keyed, so an old one is already a point-in-time snapshot. Storage is the only cost of keeping it.

Your data is not held hostage

The reason to be comfortable adopting a pre-1.0 library is not a promise about the library. It is that leaving costs you one command, and the bytes were never anywhere you could not reach.

  • ✓ The bytes are in your bucket, immutable your account Cold objects are generation-keyed and never mutated in place. Nothing is stored anywhere we control, and there is no service to be shut off.
  • ✓ The format is documented .crbm Chunked Remote BitMap — chunked because 16-bit chunks are the data model, remote because every choice in it assumes the bytes are far away and billed per request. A sequence of per-chunk payloads behind a footer index; every chunk carries a CRC32C in its index entry, verified before any deserialize, and the index and footer carry their own. The container is codec-independent — only the payload bytes belong to a flavor. Specified rather than reverse-engineered.
  • ✓ One command writes everything out exportSegments() Cross-language roaring or newline-delimited ndjson, via public read APIs only, with an export-segments CLI that wraps it. The exit is a shipped feature, not a migration project.

The benchmarks page carries the rate past which a flat tier is cheaper, the methodology, and what each measurement does and does not establish.
