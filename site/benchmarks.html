Past the crossover

Those two rows are thresholds on one axis — sustained throughput — and that axis is the only one where a flat node competes. Three of the four inputs behind them are set to their worst plausible value on purpose. Two of them can remove the crossover entirely.

What moves this line All four are inputs, not constants
Input Published as Change it and
Average item size 8 KiB DynamoDB bills writes per KiB rounded up, so an 8 KiB chunk costs eight write units rather than one. That single rounding rule is most of the 26.33. Narrower delta rows move the line by the same factor.
Hot-cache hit rate 0 Every read billed — the pessimal value, chosen so the figure cannot flatter us. A cache that actually works moves the read line by the reciprocal of the miss rate.
Warm write pricing on-demand Set the profile's per-write rate to zero and you have modelled a provisioned or flat warm tier. The write crossover disappears — there is no per-request meter left to cross.
Write topology B Topology B is live warm writes. Topology A takes writes by bulk-load instead, so it carries no per-write charge at all. The write crossover disappears.

The estimator will also tell you this itself: a batchable-writes advisory fires when the modelled write count far exceeds the number of distinct warm rows the data can occupy, because that means the same row is being rewritten repeatedly and addMany() would collapse it.

  • 01 What you give up going flat the idle price One property, and it is the headline one: paying nothing while nobody is asking. $0.03 /mo for 1.2 GiB at rest is 0.008% of a Redis node. A flat tier bills you the same whether the traffic arrives or not.
  • 02 What no pricing choice can take away 100 / 2,000 Chunk-skipping happens above the driver and above the codec — it is key arithmetic, not a storage feature. Crossing a throughput threshold does not affect it. Step through it.
  • 03 And a flat node still is not RAM for everything three tiers Cold objects stay in object storage; only the working set occupies the warm tier. A node sized for your working set is a much smaller node than one sized for your whole history — which is the comparison a single flat number hides.
  • 04 The flat tier can be one of ours Redis · Postgres · MySQL Redis is on this page twice, doing two different jobs, and the distinction matters: the baseline is someone holding the whole dataset in a Redis node's RAM, while the warm driver is Redis holding our chunk deltas. And it is a warm driver only — the corpus stays in cold object storage, so the node has to hold your recent writes rather than your whole history. That is a far smaller node than the one the baseline prices. “Use a flat tier” can mean pointing this library at something you already run. Ten drivers, warm and cold chosen separately.

Both panels share one y-axis, so they can be read against each other. The dashed line does not move — that is what paying for a node instead of for usage looks like. Where the curve crosses it is the rate in the table above.

The one latency claim we make

Throughput is too noisy to gate on shared runners, so it is not in the table above at all. This single scoped measurement is the exception.

  • 01 Warm has(), in-region p50 5.27 ms · p99 12.71 ms n = 2,000, run 2026-07-27 from AWS CloudShell in us-east-1, against the published npm package rather than a local build. Warm-only seeding with no cold generation, so every call had to reach DynamoDB and the hot cache could not mask it.
  • 02 The honest reading “p99 inside budget” Not “always fast”. A second independent run agreed on every percentile to within about 0.5 ms — that agreement, rather than either run alone, is the reason to believe the distribution. If your budget is sub-millisecond, this number is telling you to use Redis.

A hundredfold more segments, the same memory

The fear with a library that holds bitmaps is that a long-running server accumulates them until it dies. So the fleet was grown from a thousand segments to a hundred thousand, reading every one, under a fixed reader-cache cap. Retained heap is flat. That flatness is the claim — memory is a function of the cap you set, not of how much data you own.

A 100× larger fleet moved retained heap by 0.9 MiB. Intersection of two 2,000,000-id segments (2,000 chunks each, 100 shared) fetched only 100 of the 2,000 chunks per segment, in 25.3 ms. Fleet seeded at ~42–55 durable segments/s (fsync-bound). Measured on Apple M3 Pro (arm64, node v24.14.1) — discovery is filesystem-bound here, so the shape is the claim, not the absolute milliseconds.

  • 01 What is bounded retained heap Sampled after a forced GC, so it is live data rather than garbage awaiting collection. This is the column the invariant is about.
  • 02 What is not process RSS RSS grows, and we are not going to pretend otherwise. The harness seeds a hundred thousand segments inside the same process, and RSS is monotonic — it never returns pages. It is measuring the benchmark, not the bound.
  • 03 What gets worse discovery time Only the compaction daemon pays this — add, has, count and intersect never call it. Discovery can already be sharded across workers, which divides the per-segment warm scan; but the shard filter is applied after the registry enumeration, so each worker still walks every row and that walk stays O(total). A resumable cursor would bound it, and has not been built.

Method

Real services

S3 and DynamoDB in us-east-1 at on-demand rates. No LocalStack, no emulator, no simulated latency — a LocalStack rehearsal exists for mechanics and is deliberately not committed as evidence.

Metered at the wire

Operation counts come from the SDK. DynamoDB capacity comes from AWS's own ConsumedCapacity field, not from our model of what a write ought to cost.

Gated, both directions

Every figure on this page is checked against bench/results.json and docs/benchmarks.md by a build gate — and the check also fails on a figure the sources cannot account for, so a number cannot improve without evidence either.

And the estimator itself

estimateCost() produces every figure above, so its own accuracy is the claim they all rest on. Against a real measured workload its prediction lands within ±20% of the backend cost actually incurred.

What these numbers do not establish

Each of these is a real limit on what you should conclude.

  • 01 Published rates × wire-metered ops — not a cloud bill not reconciled Request tiers and storage-class transitions are unmeasured, and reconciliation against Cost Explorer is blocked on account access. This is arithmetic over real counts, which is stronger than a model and weaker than an invoice.
  • 02 Cost, not latency one scoped run One latency measurement is published above and it is scoped narrowly on purpose. Everything else on this page is a bill, not a stopwatch.
  • 03 Your region and workload move the crossover estimateCost() These are us-east-1 on-demand rates at 8 KiB items with the hot cache off. Feed your own pricing profile in and get your own crossover — the same function generates this page. How.
  • 04 The intersection window is not soak-tested no intersect in soak The long-running soak exercises the write and read paths but issues no intersect calls, so it says nothing about intersection memory over time. The measured run is a single operation, not a duration.
