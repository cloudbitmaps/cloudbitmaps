Your id-sets don't need to live in reserved RAM.

CloudBitmaps keeps large sets of user ids as compressed Roaring bitmaps in object storage you already own, holds only the working set warm, and answers membership and intersection queries from stateless functions. The axis is reserved capacity versus metered requests — not speed.

Three layers, in the order that decides it

How the sets are represented, where they reside, and what they cost while nobody is asking. The first is a property of the format and no configuration erases it. The second is why a query does not pull the corpus back. The third is where reserved capacity competes — and it does.

Layer 01 · Structure A property of the format
If the set lives in Its representation is
Redis SETBIT / BITOP A String treated as a bit array — that is all a Redis “bitmap” is. Uncompressed, one bit per id in the range, dense chunk or nearly empty one.
Redis SADD / SINTER A hash table of members. Small all-integer sets get a packed encoding, but that converts away as the set grows, leaving per-member overhead.
CloudBitmaps A decision per chunk — the table above. The two rows above this one are each one of those choices, made permanently and in advance.

Redis has no Roaring type of its own. A third-party module wraps CRoaring, but a managed Redis service generally will not load arbitrary modules — so this is not us versus Redis, it is adaptive versus a fixed representation. And because Redis is one of our own warm drivers, you can have the adaptive one inside Redis. How a chunk picks its container →

Layer 02 · Residency Corpus cold · working set warm
25.3 ms One intersection 100 of 2,000 chunks fetched
7.8 → 7.0 MiB Retained heap across 1,000 → 100,000 segments

The corpus sits in blob storage as immutable objects; only the working set is warm. An intersection compares chunk keys first and fetches only the chunks that can contribute — the rest are never requested, so they cost nothing and add no time. Reserved RAM has no equivalent move: the set is resident or it is not there. That is also why retained heap barely changes when the segment count grows a hundredfold — the engine holds keys and a bounded window, not the corpus.

Layer 03 · Idle cost Requests & compute
$0 Standing charge nobody asking, nothing charged
$0.75 /M Incremental writes one delta row per chunk, metered per request
$0.14 /M count() calls metadata only — zero payload reads
$5.88 /M Segment publishes a full generation rewrite — batch it

There is no hourly charge for a segment existing. You pay per request, and an idle segment issues none — which is the whole point when most of the corpus is read on a small fraction of requests. Storage at rest is separate, and it is the $0.03 /mo above.

This is the layer where reserved capacity genuinely competes. A flat node is a fixed price for unlimited requests, so above some rate it wins outright. That rate is below, at the same size as everything above it.

Don't use this if

You need a sub-millisecond p99 on a cache-sized working set. Warm has() is milliseconds and the distribution is above — for that job, use Redis. A RAM store answers a single membership check 10–20× faster than any warm round trip, and no configuration here changes that.

And if the answer is “both”

A flat tier can be one of our own ten drivers: run Redis as the warm tier and keep the cold corpus in blob storage. The node then holds recent chunk deltas rather than your whole history, so it is a much smaller node than the baseline prices — and you keep the tiering and the chunk-skipping.

Five operations, the ones you already call. What changes is where the bytes live and what you are billed for — not the shape of your code.

const bought = store.segment('bought-last-90d');
const opened = store.segment('opened-this-week');

await bought.add(1_234_567_890);
await bought.has(1_234_567_890); // true
await bought.count();                // exact, not estimated

// fetches only the chunks that can contribute
for await (const id of bought.intersect([opened])) { … }

intersect() takes an array, so the same call combines any number of segments. It returns an async iterable — ids stream out as the surviving chunks arrive rather than accumulating first. Install, drivers and the full API →

The data stays yours, and you can prove it

Two questions arrive before a benchmark does: what happens when someone must be erased, and what happens if we want out.

Encryption at rest · crypto-shred

Cold objects are encrypted at rest. Destroy the key and the data is destroyed with it — no rewrite pass over immutable objects, no waiting for a compaction to catch up. A later read raises a typed KeyUnavailableError rather than returning silence.

Portability · no platform

An open, documented on-disk format, written to storage accounts you own, with a documented export path off the library entirely. There is no service in the middle and no account to close — leaving is a matter of reading your own bucket. The exit is a feature, not a concession.

How the figures are kept honest

Every money figure and rate on this site is checked in CI against the sources that produced it — in both directions. A number its sources cannot account for fails the build rather than shipping quietly, so an overclaim is a broken build and not a discovery you make later.
