Many use cases, one shape.

Many ids, mostly idle, and it has to survive a restart. That’s the shape — these five are just where it turns up most often. If it describes a list you maintain, it fits, whatever you call it.

Where it fitsThe five most common
The job What’s in the set You call How it’s used
Audience segmentation user ids who bought in the last 90 days AND opened the app this week intersect rebuilt on a schedule, read on a fraction of requests
Feature-flag & experiment cohorts the ids assigned to each variant has read on nearly every request, written rarely
Permission & entitlement sets ids allowed to see a given resource has read constantly, and must survive a restart

Also fits

Fraud and abuse blocklists · event deduplication, the “have I already processed this?” set · follower and social-graph edges · consent and regional-eligibility registries · and distinct-count reporting, where count() is exact rather than a sketch with an error bar.

intersect and andNot are marked because they are the operations the tiering exists for — the ones that would otherwise pull whole sets into memory. Large means the measured run behind this page: two 2,000,000-id segments, of which an intersection fetches 100 chunks of 2,000. Step through it.

Use this when
  • Segments are large and mostly read — audience lists, feature cohorts, permission sets.
  • They must survive restarts and cost nothing while nobody is asking.
  • Your compute is stateless and you would rather not run a node at all.
  • The set is bigger than you want to keep resident, or heading that way, and sizing a node for its growth is the part you would rather not do.
  • You need exact cardinality — not a sketch with an error bar — and you need it without reading the payload.
  • The bytes have to stay in your own storage account, in a documented format, with a way out that does not involve us.
  • Someone may have to be erased on request, and rewriting immutable objects to do it is not acceptable.
Use something else when

You need a sub-millisecond p99.

Not just on hits. Our hot tier is in-process RAM, but a miss is a network hop — warm has() is 5.27 ms at p50 and 12.71 ms at p99. A sub-millisecond tail needs the whole set resident, which is a different machine.

Your ids aren’t 32-bit integers.

An id is a u32. UUIDs and string keys need a dense-integer mapping that you own and operate — a second store, and a real cost if you don’t have one.

For the first one that usually means Redis — Redis as your set store, which is a different thing from Redis as one of our warm drivers.

Three tiers, one API

A segment lives in all three places at once. You call has(); the store decides where the answer comes from.

Your call

addMany([75, 99_999, 1_234_567_890])

  • 75→ key 0x0000
  • 99_999→ key 0x0001
  • 1_234_567_890→ key 0x4996

3 ids · 1 segment · grouped by key before any write

Chunk keys3 of 2,000

32-bit id → 16-bit key + 16-bit remainder

The read comes back out intersect(shoppers, active) fetches 100 / 2,000 chunks — 1,900 are never requested → 100,000 ids

HOT · RAM

A bounded LRU of decoded chunks inside your process. Nothing is pinned; nothing is required.

WARM · NoSQL

Per-chunk delta rows — adds and removes since the last publish. This is what makes writes cheap.

COLD · .crbm

Immutable, generation-keyed objects in your own bucket. Documented format, one-command export.

The part that is hard to copy

Intersecting two 2,000,000-id segments does not download two segments. Chunk keys are compared first, and only chunks whose keys appear in both are ever fetched — 100 of 2,000, in 25.3 ms. The other 1,900 stay cold and unbilled.

quickstart.tsNo setup
import { CloudRoaring, MemoryWarmDriver, MemoryColdChunkSource } from '@cloudbitmaps/roaring';

const store = new CloudRoaring({
  warm: new MemoryWarmDriver(),
  cold: new MemoryColdChunkSource(),
});

const vips = store.segment('high-value-shoppers');
await vips.addMany([75, 99_999, 1_234_567_890]);
await vips.has(1_234_567_890);  // true

You could build this yourself. Here's the part that takes a year.

Sharding a bitmap across object storage is a weekend. Making it correct under concurrent writes, deletes and compaction is not.

Rolling it yourself

  • ✕A chunking scheme only your code can read, undocumented and unversioned
  • ✕Whole-blob GET, decode, modify, PUT — the write cost scales with the segment, not the change
  • ✕An OR-merge that cannot express a delete, so removals need a full rebuild
  • ✕Two concurrent compactions that silently drop whichever writes landed mid-scan

With CloudBitmaps

  • ✓A documented .crbm format, generation-keyed and immutable, with a one-command export
  • ✓Per-chunk delta rows: $0.75 per 1M incremental writes, and nothing at all when idle
  • ✓Tombstones are first-class — a real remove(), merged as (cold ∪ adds) \ removes
  • ✓Compaction purges conditionally on the version it archived, so post-scan writes survive

Every row on the right is a hard invariant with named tests, not a design intention — 1,156 of them run on every commit.
