Your id-sets don't need to live in reserved RAM.

CloudBitmaps keeps large sets of user ids as compressed Roaring bitmaps in object storage you already own, holds only the working set warm, and answers membership and intersection queries from stateless functions. The axis is reserved capacity versus metered requests — not speed.

Three layers, in the order that decides it

How the sets are represented, where they reside, and what they cost while nobody is asking. The first is a property of the format and no configuration erases it. The second is why a query does not pull the corpus back. The third is where reserved capacity competes — and it does.

Redis has no Roaring type. It gives you Sets, which carry per-member overhead, or Bitmaps — a String treated as a bit array, uncompressed. Neither compresses a sparse id-space.

A third-party Roaring module exists, and a managed Redis will not load it. So on a managed node this is not a setting you can change — which is what makes structure the first layer rather than an optimisation.

How a chunk picks its container →

Layer 02 · Residency Corpus cold · working set warm
25.3 ms One intersection 100 of 2,000 chunks fetched
7.8 → 7.0 MiB Retained heap across 1,000 → 100,000 segments

The corpus sits in blob storage as immutable objects. Only the working set is warm. An intersection compares chunk keys first and fetches only the chunks that can contribute to the result — the rest are never requested, so they cost nothing and add no time.

Reserved RAM has no equivalent move: the set is resident or it is not there. That is also why retained heap barely changes when the segment count grows a hundredfold — the engine is holding keys and a bounded window, not the corpus.

There is no hourly charge for a segment existing. You pay per request, and an idle segment issues none — which is the whole point when most of the corpus is read on a small fraction of requests. Storage at rest is separate, and it is the $0.03 /mo above.

This is the layer where reserved capacity genuinely competes. A flat node is a fixed price for unlimited requests, so above some rate it wins outright. That rate is in the next panel, at the same size as everything above it.

Past these sustained rates a flat reserved node is simply cheaper, and we publish the figures rather than let you find them. They are properties of the warm tier you chose, not of the engine — a different tier moves them, which is why each is quoted with its topology.

Don't use this if you need a sub-millisecond p99 on a cache-sized working set. Warm has() is milliseconds and the distribution is beside it — for that job, use Redis.

And if the answer is “both”, a flat tier can be one of our own ten drivers: run Redis as the warm tier and keep the cold corpus in blob storage. The node then holds recent chunk deltas rather than your whole history.

Three tiers, one API

A segment lives in all three places at once. You call has(); the store decides where the answer comes from.

HOT · RAM

A bounded LRU of decoded chunks inside your process. Nothing is pinned; nothing is required.

WARM · NoSQL

Per-chunk delta rows — adds and removes since the last publish. This is what makes writes cheap.

COLD · .crbm

Immutable, generation-keyed objects in your own bucket. Documented format, one-command export.

Intersecting without downloading

Intersecting two 2,000,000-id segments does not download two segments. Chunk keys are compared first, and only chunks whose keys appear in both are ever fetched — 100 of 2,000, in 25.3 ms. The other 1,900 stay cold and unbilled.

A Set, with a different address

Five operations, the ones you already call. What changes is where the bytes live and what you are billed for — not the shape of your code.

  • add
  • has
  • remove
  • count
  • intersect
segments.ts@cloudbitmaps/roaring 
const bought = store.segment('bought-last-90d');
const opened = store.segment('opened-this-week');

await bought.add(1_234_567_890);
await bought.has(1_234_567_890); // true
await bought.count();                // exact, not estimated

// fetches only the chunks that can contribute
for await (const id of bought.intersect([opened])) { … }

intersect() takes an array, so the same call combines any number of segments. It returns an async iterable — ids stream out as the surviving chunks arrive rather than accumulating first.

The data stays yours, and you can prove it

Two questions arrive before a benchmark does: what happens when someone must be erased, and what happens if we want out.

Encryption at rest · crypto-shred

Cold objects are encrypted at rest. Destroy the key and the data is destroyed with it — no rewrite pass over immutable objects, no waiting for a compaction to catch up. A later read raises a typed KeyUnavailableError rather than returning silence.

Portability · no platform

An open, documented on-disk format, written to storage accounts you own, with a documented export path off the library entirely. There is no service in the middle and no account to close — leaving is a matter of reading your own bucket. The exit is a feature, not a concession.

How the figures are kept honest

Every money figure and rate on this site is checked in CI against the sources that produced it — in both directions. A number its sources cannot account for fails the build rather than shipping quietly, so an overclaim is a broken build and not a discovery you make later.
