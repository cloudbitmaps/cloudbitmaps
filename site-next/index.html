Big bitmaps on object storage.

No daemon. No second service. One bucket.

CloudBitmaps keeps large id-sets as immutable objects in storage you already own, and reads only the chunks a query can match — 100 of 2,000. The reads are the calls you know: has · count · iterate · intersect · union · andNot.

02 · The write model

Writes arrive as whole generations.

There is no add and no remove. A segment changes only when something upstream publishes a new one. If you need per-id writes, you can rule us out here.

03 · Chunk-skipping

100 of 2,000 chunks. The other 1,900 are never requested.

Keys are compared from each segment's index before any chunk is requested. Only a chunk whose key appears in every operand is fetched — the rest are never requested and never billed.

05 · Does this fall over

Retained heap does not grow with the fleet.

With the reader cache capped at 1,024 segments, retained heap stays flat from a thousand segments to a hundred thousand. Process RSS does grow — the benchmark seeds every segment in the one process — and so does discovery, an honest O(total) scan. All three sit on the same row.

Under it, the protocol is written down as 7 hard correctness invariants — write-once generations published forward-only, one generation per read, a GC that never touches the current one, every tier byte untrusted — each with named tests that run on every commit.

06 · Fit

Where it fits, and where Redis is better.

Use this when

The set is large, mostly read, and computed in batches.

Audience lists, feature cohorts, permission sets — bigger than you want to keep resident, and produced by something upstream: a warehouse query, a nightly job, a combine of two other segments.

It has to survive a restart, and cost next to nothing while idle.

The corpus outlives any one process, your compute is stateless, and you would rather not run a node at all just so the set is there when something asks.

The data has to stay yours.

Segments are immutable objects in a bucket you already own.

Use Redis instead when

You need a sub-millisecond p99.

Our cache tier is in-process RAM, but a miss is a ranged GET against object storage. A sub-millisecond tail needs the whole set resident — that is a different machine.

The set changes one id at a time.

There is no add and no remove here: a segment changes only by publishing a whole new generation. Accumulate per-id writes where they arrive — Redis is good at that.

You read past 329.15 GETs a second, every one a cache miss.

Above that rate a flat cluster is cheaper. The chart above says so, and so does the benchmarks page, with what the cache hit rate does to the line.

A codec, a storage, one bucket.

Install the codec you want and the storage you have. The memory drivers need nothing at all, so you can see the shape before you point it at a bucket.

Ids are 32-bit unsigned integers. UUIDs and string keys need a dense-integer mapping that you own — worth knowing before you install.
