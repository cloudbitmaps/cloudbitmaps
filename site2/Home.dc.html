Your id-sets don't need to live in reserved RAM.

CloudBitmaps keeps large sets of user IDs as compressed Roaring bitmaps in object storage you already own, holds only the working set warm, and answers membership and intersection queries from stateless functions. The axis is reserved capacity versus metered requests — not speed.

Three layers, in the order that decides it

How the sets are represented, where they reside, and what they cost while nobody is asking. The first is a property of the format and no configuration erases it; the second is why a query doesn't pull the corpus back; the third is where reserved capacity competes — and it does.

The thresholds come after all three, because a threshold without the structure around it is just a number. Layer 01 depends on the codec you install — pick it on the right and this section follows. Layers 02 and 03 sit above the codec and do not move.

The corpus sits in blob storage as immutable objects. Only the working set is warm. An intersection compares chunk keys first and fetches only the chunks that can contribute to the result — the rest are never requested, so they cost nothing and add no time.

Reserved RAM has no equivalent move: the set is resident or it is not there. That is also why retained heap barely changes when the segment count grows a hundredfold — the engine is holding keys and a bounded window, not the corpus.

There is no hourly charge for a segment existing. You pay per request, and an idle segment issues none — which is the whole point when most of the corpus is read on a small fraction of requests. Storage at rest is separate, and it is the $0.03/mo above.

This is the layer where reserved capacity genuinely competes. A flat node is a fixed price for unlimited requests, so above some rate it wins outright. That rate is published in the next panel, at the same size as everything above it.

Past these sustained rates a flat reserved node is simply cheaper, and we publish the figures rather than let you find them. They are properties of the warm tier you chose, not of the engine — a different tier moves them, which is why each is quoted with its topology.

Don't use this if you need a sub-millisecond p99 on a cache-sized working set. Warm has() is milliseconds and the distribution is above — for that job, use Redis.

And if the answer is “both”, a flat tier can be one of our own ten drivers: run Redis as the warm tier and keep the cold corpus in blob storage. Estimate it on your own rates — the estimator lands within ±20% of a real bill.

The data stays yours, and you can prove it

Two questions arrive before any benchmark does: what happens when someone must be erased, and what happens if we want out.

ENCRYPTION AT REST · CRYPTO-SHRED

Cold objects are encrypted at rest. Destroy the key and the data is destroyed with it — no rewrite pass over immutable objects, no waiting for a compaction to catch up.

This is usually the first question a company asks, so it is on the home page rather than three clicks in.

PORTABILITY · NO PLATFORM

An open, documented on-disk format, written to storage accounts you own, with a documented export path off the library entirely.

There is no service in the middle and no account to close. Leaving is a matter of reading your own bucket — the exit is a feature, not a concession.

How the figures are kept honest

Every money figure and rate on this site is checked in CI against the sources that produced it — in both directions. A number its sources cannot account for fails the build rather than shipping quietly, so an overclaim is a broken build and not a discovery you make later.
