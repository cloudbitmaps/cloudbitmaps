You are paying a database to remember lists nobody is reading.

Audience segments, feature cohorts, permission sets, users-who-did-X. They sit in a Redis node sized for the largest of them, billed every hour, and each new segment makes the node bigger. CloudBitmaps keeps those lists in your own S3 bucket and answers set queries from stateless functions — same Set-shaped API, no node to keep alive, no RAM ceiling.

Three axes decide whether this suits you

How much you can afford to keep, how cheaply you can intersect it, and what it costs while idle. Two of them are lopsided in our favour. The third is a real trade, and it is printed at the same size as the other two.

Redis needs the whole set resident. We don't — so sets far larger than your RAM are simply not a problem, and the ones you already have cost 0.008% of the node they were living on.

This is the axis that changes what you are willing to keep at all. Segments you would have trimmed, expired or never built because the node would have to grow can now just exist.

The obvious objection to sets in a bucket is that answering a query means pulling them back. It doesn't. Chunks that cannot contribute to the result are never requested.

This is key arithmetic, and it happens above the storage driver and above the codec — so no driver you pick and no flavor you install can take it away. It is the part of this design that is hard to copy.

There is no hourly charge for existing — you pay per request, and an idle segment issues none. Storage at rest is not free, it is axis 01's $0.03/mo; what goes to zero here is the request and compute side.

This is also the one axis where a flat Redis node genuinely competes. Past 26.33 sustained writes a second it wins outright, and we publish that rather than let you discover it.

Two things about that ceiling: it is 2.27 million segment updates a day, which cohorts rebuilt on a schedule are rarely close to — and the write meter is a property of the warm tier you chose, not of the engine, so a cheaper tier moves it. That is why the figure is quoted with its topology. Run estimateCost() on your own rates rather than trusting ours.

Not a cost question at all, but the other genuine exclusion: a sub-millisecond p99 on a working set that fits in RAM is a different machine, and no version of this library will be it.

This is pre-1.0 and has one maintainer. The honest risk is operational maturity, not losing your data: the objects are immutable, the format is documented, and they are already in your bucket.
