# `scripts/` — the build, the release, and the gates

Most of what keeps this repository honest lives here: the package build, the release machinery, and a set of
gates that each exist because something goes wrong without them. Every script opens with a header comment
explaining **why** it exists — the specific failure it prevents. Read that before changing one.

"When" below means: **CI** — on every pull request, from `.github/workflows/ci.yml`; **release** — from
`.github/workflows/release.yml` on a tag; **by hand** — a `pnpm` script someone runs deliberately; **by other
code** — imported or sourced by another script or a test.

## Build and package

| script | what it does | when |
|---|---|---|
| `build.mjs` | The package build: bundles each package's entries with esbuild, ESM only; emits declarations with `tsc`; rewrites the `@/…` self-alias in the emitted `.d.ts` into relative paths; and gives every relative specifier there its `.js` extension, without which a consumer's TypeScript silently resolves those types to `any`; last, deletes every emitted `.d.ts` that no `exports` entry reaches, so internal modules ship no declaration. | CI, release — `pnpm build`, which runs it in every package |
| `api-surface.cjs` | The gate on public type signatures. Reads the declarations the build emitted for every entry point in each package's `exports` map, and writes one sorted line per exported symbol and per member, each with its full signature text. A class that declares no constructor is recorded with the one it inherits, or with `constructor();` when its chain declares none, and a private constructor as declared. `--check` fails if the built surface is not the committed snapshot in `api-surface/`; `--against <ref>` fails if an entry is removed, changed or added against the snapshot committed at that ref (a new `(referenced)` key, a type a public signature names and no entry exports, included), unless `api-surface/allowed.json` names it with a reason in a row the ref does not already have (a `Name*` row covers `Name` and its members, never `NameOptions`). An entry a package lists in its manifest's `cloudbitmaps.internalEntries` is outside the promise: it is left out of `surface.json`, its lines go to `api-surface/internal.json` (which `--check` also keeps current), and making an entry internal needs the row `<specifier> (internal)`. | CI, release — `pnpm api:surface:check`; the `api-surface-base` workflow on a pull request — `--against` the base branch, with no build; by hand — `pnpm api:surface` regenerates the snapshot |
| `function-length.cjs` | The function-length gate: no function in `packages/*/src` is over 100 code lines (blank and comment-only lines not counted), and the ones that already are can only shrink. Measures every function with ESLint's parser, identifies each by file and enclosing names rather than line number, and compares the over-limit ones with `function-length-baseline.json`: a new offender, a baselined function that grew, and one that shrank without its entry being lowered or removed all fail. `--update` lowers or drops entries (never records growth) and `--list` prints today's offenders. Its header comment states the limits. | CI, as part of `pnpm lint` (`pnpm lint:fn-length` alone) |
| `function-length-baseline.json` | Every function over 100 code lines today, with its size: the ratchet `function-length.cjs` compares against. An entry is removed once its function is at or under the limit. | read by `function-length.cjs` |
| `test-no-dist.cjs` | `pnpm test:no-dist [vitest arguments]`: the unit suite with every `packages/*/dist` hidden, as CI's test step has it (CI runs the tests before the build, so no package has a `dist/` there). A test that resolves a package through its `dist/` (an `exports` path, a spawned `node` that resolves a package, a script that imports a built entry) passes on a machine with an old build and fails only in CI. It hides each `dist/` through `lib/no-dist.cjs`, runs `vitest run` with the arguments given (a file, `-t`, `--maxWorkers=2`), and restores every `dist/` when the run ends, fails or is interrupted; `--restore` alone puts back what a killed run left (it refuses while a run is live), and the next run does that first. The folders are absent for the whole run in every terminal, so build nothing meanwhile. A build that cannot go back (its package has a `dist/` again, or is gone) is moved to `.no-dist-aside/kept/`, never deleted. `tests/scripts/test-no-dist.test.ts` runs it on a temporary tree with a planted test. | by hand — `pnpm test:no-dist` |
| `smoke.cjs` | The built packages must import cleanly on real Node, through the `exports` map a consumer resolves, with the TypeScript codec round-tripping a load and the main entries free of any cloud SDK, and core's main entry, `driver-kit` and the tools free of any Node builtin and loadable in a context without one; and the shipped declarations must equal what the TypeScript compiler loads for a consumer importing every entry by package name under NodeNext, Bundler and Node10 resolution (skipLibCheck off): it fails on any diagnostic inside a `dist/` (a lost declaration is TS2307), any diagnostic in the probe itself (a lost entry is TS7016 or TS2307 on its import), any stray `.d.ts` no mode loads, and any declaration loaded from outside this checkout (a worktree nested in another checkout can resolve a package through the outer `node_modules` and so load a file this build did not ship, without a diagnostic), naming the files. The compiler reads only the `typesVersions` range its own version selects; the walk reads them all. The check is independent of the build's prune walk. In the same three modes it compiles, on its own, every import from a workspace package on the README, the guides, the package READMEs and the site, so a sample cannot import a name its package does not export (a name the flavor stopped exporting is said to be one), the API reference's block of derived port types, each alias held to the port its comment names, and the typed fixture `tests/smoke/typed-surface.ts`, which names every type `@cloudbitmaps/roaring` exports and reads `BudgetExceededError`'s typed fields. It fails when the flavor exports a type the fixture does not name (or one it stopped exporting, `tests/docs/left-the-flavor.json`), when a line starts an import of a workspace package that does not parse, and when it finds fewer than 50 imports. | CI, release — `pnpm smoke` |
| `consumer-install.cjs` | Installs the packages the way a user does. On the host it builds the workspace and runs `pnpm pack` on each of the six (so `workspace:*` becomes the exact version, as at publish). With `--image <image>` it then starts a throwaway container of that Node image, with the tarballs and the script mounted read-only and nothing else: no environment passed in, no capabilities, no Docker socket, no home or workspace mount. Inside, npm installs the six tarballs together, so the cloud SDKs come from the registry with no lockfile and their install scripts run, retried twice on a failed install; the project's `package.json` is bare, because the six packages have no install script to allow. It fails on a `workspace:` left in a packed manifest, on any package not installed exactly once, and on an `exports`, `bin`, `typesVersions` or `files` entry missing from a tarball or an empty `dist`; then it runs one program as ESM and again as CommonJS that imports every entry by name, resolves each `package.json`, loads ids into a store on the in-memory driver and on the local-files driver and reads them back (`has`, `count`, an intersect), and runs the installed `export-segments --help`. No cloud is contacted: the drivers are imported, not used. `--no-container` runs the second half on the local machine, for local use only: it runs third-party install scripts there, and refuses to run when `CI` is set. It does not compile types in the project (`smoke.cjs` does) or install with pnpm or yarn. `smoke.cjs` loads the built packages inside the workspace, where pnpm links them and `files` is never consulted; this reads only what a tarball holds. | CI (`consumer install`, Node 22 and 24, every pull request and push to `main`); not the release workflow |
| `sdk-floor.cjs` | Runs one storage driver's tests against the oldest cloud SDK its dependency range allows. `--driver s3`, `gcs` or `azure-blob` reads the lowest version of each alternative of that package's range out of its `package.json` (`--floor <n>` takes the n-th, 0 the lowest, and is required when a range written with `||` has several; `--version <v>` names another version), exports the committed tree with `git archive HEAD` into a new directory outside the checkout (it refuses to run inside it), adds a `pnpm.overrides` entry pinning the SDK, runs `pnpm install --no-frozen-lockfile` there, and fails unless every installed copy of the SDK (the root's, the driver package's, and any in `node_modules/.pnpm`) is exactly that version (a pin that silently did not take would test the newest SDK and report green). Then it runs `tests/drivers/<driver>/` and, with `--integration`, the driver's file under `tests/integration/` against the emulator that is already up (`--integration-only` runs that file alone). The directory is removed whatever happened (`--keep` leaves it). The repo's pnpm settings are kept, so the only dependency build script that runs is `roaring`'s. `--expect-failure <text>` makes it a negative control: the tests must fail and a failure message must contain `<text>`; a pass, a failure for another reason and an install or version-check failure all fail the control. A range it cannot read (no lower bound, a `>`, a tag) is refused rather than guessed, and so is an empty `--version` or `--expect-failure` (an empty text would match any failure). The install gets 4 minutes and each test run 7, so one install and both test runs fit inside the job's 25; a command past its budget is killed together with every process it started (its process group), and the run fails. Run one leg by hand with `node scripts/sdk-floor.cjs --driver s3` (the unit half needs no Docker; `--integration` needs the driver's emulator, from `docker compose up -d`). What it proves: the driver works with the oldest SDK its range lets a user resolve, and, through the control, that the job can see an S3 SDK that sends no `If-Match`. What it does not: the SDK's own dependencies resolve to their newest in range, the types are not compiled against the floor, and npm 12 is untested. | CI (`sdk-floor.yml`, nightly at 03:00 UTC, on demand, and on a pull request that touches a driver, the driver kit, a driver's tests, the shared test helpers, the lockfile, the root `package.json`, the vitest configs, the emulators' start, the script or the workflow; the workflow sets `cache-mode: read`, so it cannot write the cache) |
| `dts-specifiers.cjs` | The detector behind "every relative specifier in an emitted `.d.ts` carries its extension" — without one, a consumer's TypeScript cannot resolve the published types. | by other code — `build.mjs`, `smoke.cjs`, and `tests/arch` |
| `builtin-free.cjs` | The detectors behind "core's main entry, `driver-kit` and the tools import no Node builtin", the other half of hard invariant 7: a scan of every built file the entry reaches for a `node:` specifier, and a load of the entry bundled for a platform with no builtin, in a context holding only the globals a V8 isolate has. Each layer catches what the other cannot; its header has the table and the limits. | by other code — `smoke.cjs` and `tests/arch` |
| `js-tokens.cjs` | The one reader behind the specifier detectors and the module-graph walk: the TypeScript parser's tree, so a string is a string-literal node and a comment is attached trivia, with no guess at what a `/` means and no pairing of quotes (a regular expression literal holding a quote, or a division after `opts.type`, cannot hide what follows). `sdk-specifiers.cjs` and `builtin-free.cjs` read their string literals through it, and `dts-specifiers.cjs` blanks comments through it. | by other code — `sdk-specifiers.cjs`, `builtin-free.cjs` and `dts-specifiers.cjs` |
| `sdk-specifiers.cjs` | The detector behind "the main entry stays SDK-free", one of the hard invariants in `AGENTS.md`. | by other code — `smoke.cjs` and `tests/arch` |
| `doc-imports.cjs` | The detector behind "every import a guide shows compiles": the pages a reader copies samples from (the README, `docs/guide/`, each package's README, the site's HTML pages through their markup and `site/llms.txt`), each import from a workspace package in them (named bindings on one line or many, in a list item, a block quote or after a comment, a namespace import, a default import), and each line that starts such an import and does not parse. Its header says what it does not read. | by other code — `smoke.cjs` and `tests/arch` |
| `runtime-floor.cjs` | The detectors behind the declared Node floor (`>= 22.12`). A `node-version:` pin in a workflow must resolve at or above it — `22` passes, because it means the latest 22.x; `22.11` does not — and a prose statement of the floor in the docs `tests/ci` reads must state exactly it. `node-version: 22.11`, a quoted `"20"`, a pin with a trailing comment, and phrasings like `Node.js >= 20` are each caught, where a looser pattern passes them green. | by other code — `tests/ci` and `tests/arch` |

The detector modules are split out of what uses them — `build.mjs` and `smoke.cjs`, and for the floor, a
test — so that `tests/arch` can fire each one at planted inputs and watch it catch them. In the words of
`sdk-specifiers.cjs`: **a detector nothing tests is a check that cannot be trusted.** `dts-specifiers.cjs` has a
second reason: the build rewrites exactly what the smoke test detects, so both import one scanner and cannot
disagree.

## Release and supply chain

See [`RELEASING.md`](../RELEASING.md) for how these fit together into a release.

| script | what it does | when |
|---|---|---|
| `bootstrap-publish.cjs` | Creates a package **name** that does not exist on npm yet. The release pipeline publishes tokenlessly through a Trusted Publisher, and a Trusted Publisher cannot be bound to a name that has never been published — so the first version of each new name has to be published by hand. | by hand — `pnpm release:bootstrap` |
| `changelog-section.cjs` | Prints one version's section of `CHANGELOG.md`, which the release job feeds straight into the GitHub Release — so the release notes and the changelog cannot drift apart. Fails loudly rather than publishing empty notes. | release, twice: before publishing, to prove the section exists, and again to write the notes |
| `audit.cjs` | Wraps `pnpm audit --prod` and fails only on a **production** advisory at or above `high` that has not been triaged. Triaged advisory ids live in `package.json`, under `pnpm.auditConfig.ignoreGhsas`, with the reasoning in `SECURITY.md`. It also fails, with exit 2, if the audit itself cannot run. | CI, release — `node scripts/audit.cjs`, or `pnpm run audit`. Bare `pnpm audit` is pnpm's own built-in command, and does not run this. |
| `leak-scan.cjs` | Scans every tracked file for credentials and for project-specific strings that must never become public. `--history` scans every blob reachable from every ref instead, and `--dir <path>` any directory, such as an unpacked tarball. `--snapshot` turns the migration findings — references to the old repository and to private documents — from notes into failures, and refuses to run without extra strings. Extra strings come from a gitignored `.leak-needles` file (in a linked worktree with none of its own, the main worktree's) or the `LEAK_SCAN_EXTRA` variable, and matches against them are reported redacted. AWS account ids (any standalone 12-digit run) and ARNs are refused by the built-in rules. | CI — `pnpm leak-scan`; and by other code — `leak-scan-tarballs.cjs` |
| `pr-text-scan.cjs` | Checks a pull request's public text: its title, its body, the name of its head branch and the messages of its own commits (`git log BASE_SHA..HEAD_SHA`: the pull request's own commits, those that reached its branch through a merge's second parent, and its merge commits; BASE_SHA is the base branch's tip when the branch was last pushed, so the commits a merge of the base branch brought in are not read; a squash merge copies the commit subjects into `main`'s history), and the author and the committer of each commit (name and email). It fails on a phrase that says who or what did the work (the list, with the reason for each entry, sits beside it in the script: `subagent`, `coordinator`, `this session`, `cannot spawn`, `Generated with` as a footer, `Co-Authored-By`, the whole word `Claude`, `AI-generated`, and `builder` beside a work verb; not `agent` and not `builder` alone, which are ordinary words; a phrase wrapped over two lines counts), naming the phrase, the source and the line number, never the line. A commit trailer is skipped only when it names `dependabot[bot]`, `renovate[bot]` or `github-actions[bot]`: every other `[bot]` trailer is scanned. An author or committer fails when it names a bot not on that list, `(aider)` or an Anthropic no-reply address; a person named Claude passes. The private needles alone are run over each author's and committer's name and email, in a second pass that keeps only the needle findings (so the leak scan's email rule never fires on an ordinary address); a needle finding names the commit and the field, never the value, and a field that several needles match is named once (the leak scan names ten files per rule, so the fields beyond ten are counted, not named, once per needle), and a bot, `(aider)` or address finding names the commit and whether it is the author or the committer. The phrase list and the leak scan run over the branch name too, the phrase list also with `-`, `_`, `/` and `.` read as spaces (`this-session` is found, `coordinator-free` and `docs/claude-md-notes` are not), and a branch that starts with `claude/`, `codex/`, `copilot/`, `cursor/` or `devin/` (any case, at the start of the name only) is refused; a branch name holding a twelve-digit run (a `yyyymmddhhmm` stamp) fails the account-id rule, and the fix for any branch finding is to push the work to a branch with another name and open the pull request from it. It also writes the same texts into a temporary directory and runs `leak-scan.cjs --snapshot --dir` over it, so credentials, local paths, account ids, private-repo and private-doc references and the private needles apply to PR text as to tracked files. The leak scan's report is printed with each finding's text withheld and the needle's number dropped; the leak scan itself prints a needle that is not a valid regular expression by its place in the list only, never its text, and exits 2. Commit records are read with `git log -z`, so no text in a message can end a record, and a record that does not parse is exit 2. With no needles configured (a fork's pull request gets no secrets) it runs the scan without `--snapshot`, prints that the needles were not applied and the informational findings, and does not fail for that alone; when `REQUIRE_NEEDLES` is `true` (the workflow sets it for a pull request from this repository, other than dependabot's) missing needles are exit 2. It fails closed: a missing input (in CI, a missing or empty `PR_BRANCH`, `BASE_SHA` or `HEAD_SHA` too), a git error, or a scan that crashes is a failure (exit 2), a finding is exit 1. Run it locally with `PR_TITLE="the title" PR_BODY="$(gh pr view N --json body -q .body)" PR_BRANCH="$(git branch --show-current)" node scripts/pr-text-scan.cjs`, adding `BASE_SHA=$(git merge-base origin/main HEAD) HEAD_SHA=$(git rev-parse HEAD)` for the commits; a local run applies the private needles only when a `.leak-needles` file exists in the checkout (a linked worktree reads the main checkout's), and without one it is weaker than CI. Known false positives, and the rewording for each: quoting the leak scan's own sample lines (a connection string with a password, an ARN prefix) or the contributing guide's review step (say "reviewers"); `a builder pattern` or `the builder ran` about a build tool (say "the build helper"); `coordinator` in the distributed-systems sense (say "the transaction manager"); `this session's` in a benchmark sense (say "this run's"). It does not catch a phrase that is not on the list, a leak that has been reworded, an author whose identity names no tool, a phrase inside an author's or committer's name (only a bot, `(aider)` or a vendor address is checked there), a phrase in a branch name written with underscores where the phrase has hyphens (`co_authored_by`, `ai_generated`, `docs/generated-with-x`), a branch of another tool than the five named, a NUL in a commit message (git stops reading the message at it; only a hand-built commit holds one), or anything in a comment or review. A same-repository pull request runs its own copy of the script with the secret, so the check guards against a slip, not against a hostile author. Push mode (`--push <remote name>`, run by `.husky/pre-push` once per push, however many refs) checks what a push carries before it leaves the machine: git's lines (`<local ref> <local sha> <remote ref> <remote sha>`) arrive on stdin, `PR_TITLE`, `PR_BODY`, `PR_BRANCH`, `BASE_SHA` and `HEAD_SHA` are not read, a deleted ref is skipped, and it scans every message, author and committer of the commits that are not already on the remote (`git log <tips> --not --remotes=<remote> <old tips>`: a rebase onto a moved `main`, a merge of `main` and a stale `origin/main` do not widen it, a force-push reads only the new commits; the hook never fetches, so an older remote-tracking ref only means more commits are read; a remote with no tracking refs in the clone is measured from `origin/main`, and with none the push is refused, exit 2) and the name of each pushed ref as the remote shows it (`remote ref`, not the local name: a branch name, a tag name, and an annotated tag's message and tagger), with the same rules, redaction and exit codes (a line it cannot read, a git error or a crash is exit 2, a finding exit 1). It does not see a title or a body (written after the push, so CI keeps checking them) and a run takes about a quarter of a second end to end (0.2 s for one branch, 0.26 s for a five-ref push; measured), `node` having to be on the `PATH`. The check is not a required one: that is a repository setting. `tests/ci/pr-text-scan.test.ts` fires it at planted texts and holds the workflow's trigger types, permissions, absence of a cache or install, and env-passed text in place, and runs push mode and the pre-push hook against throwaway repositories (a clean range, a finding in a message, an identity or a branch name, a new branch, an existing remote tip with a finding in its range, a remote tip this clone lacks, a diverged force-push, a rebase onto commits the remote has, a first push to a remote with no tracking refs, a deleted ref, several refs in one run, the remote-side name for a detached HEAD and a renamed push, a tag and an annotated tag's message and tagger, `node` missing from the `PATH`, a linked worktree, a line that cannot be read; each asserting the exit code). | CI (`pull request text`, every pull request, also when its title or body is edited); `git push` (`.husky/pre-push`, push mode) |
| `leak-scan-tarballs.cjs` | The same scan over the **packed npm tarballs** — what actually ships, which includes built output and sourcemaps the tracked-file scan cannot see. | CI, release — `pnpm leak-scan:tarballs` |
| `verify-roaring-prebuilt.cjs` | `roaring` is no dependency of `@cloudbitmaps/roaring`, but it is still the root devDependency the oracle compares the codec with, and it downloads a prebuilt native binary at install time on every runner, which our signed publish does not cover. This records that binary's checksum per platform and fails when it changes. With `--strict`, as CI runs it, a platform with no recorded checksum fails too; without it, an unrecorded one prints a line to record and passes. It goes with the oracle's `roaring` install. | CI — the `cross-os` job, on macOS, Windows and Ubuntu; `release.yml`, right after its install |
| `roaring-prebuilt-checksums.json` | The checksums `verify-roaring-prebuilt.cjs` compares against. | read by `verify-roaring-prebuilt.cjs` and `tests/ci` |

## Deployability and memory

| script | what it does | when |
|---|---|---|
| `lambda-smoke.sh` | Proves the **packed** library loads on AWS Lambda's Amazon Linux 2023 runtime. It packs core and the flavor, unpacks them into a `node_modules` on the host, mounts that into the runtime image, checks the packed manifests and files for native code on the host (`check-no-native-package.cjs`), and there checks that no native addon is installed and loads and round-trips the library under both `import` and `require()`. Nothing is built or installed in the container. CI runs it on x64. | CI — `pnpm lambda-smoke` |
| `lambda-smoke.mjs` | The half of the Lambda smoke that runs inside the container: the no-addon check, then the load and round-trip. | by other code — `lambda-smoke.sh` |
| `check-no-native-package.cjs` | Fails when an unpacked package could bring native code to a deployment: a manifest that names `roaring` or a native build helper in a field an install follows, sets `gypfile` or runs an install-time script, or a tree that holds a `.node` file or a `binding.gyp`. The Lambda smoke and the layer build run it on the packed tarballs, where nothing is installed and a dependency leaves no file behind. | by other code — `lambda-smoke.sh`, `build-lambda-layer.sh` |
| `build-lambda-layer.sh` | Builds a ready-to-attach Lambda **layer** holding `@cloudbitmaps/core` and `@cloudbitmaps/roaring`: JavaScript only, the same for x64 and arm64, with nothing compiled. It refuses a layer whose packages hold an addon or depend on a native package (`check-no-native-package.cjs` reads the packed manifests as well as the files), zips it, then loads the unpacked layer from `/opt` in the Amazon Linux 2023 image through `NODE_PATH`. The storage drivers are left out on purpose: which one a function talks to is its own dependency, and bundling all three would put every cloud SDK in every deployment. | by hand — `pnpm build-lambda-layer`; CI's `lambda-layer` job builds and uploads it when the workflow is run manually |
| `rss-gate.sh` | The hard memory ceiling: runs the soak (`bench/soak.cjs`) under a 384 MiB cgroup limit with swap disabled, so the limit is a true bound on resident memory — including what a heap sample cannot see. It stages the built packages as they are: there is no native addon to build, and the bench's work-folder helper and its sentinel beside the soak. An OOM-kill fails the build, and so does the soak's own verdict on slower memory creep. Records its run to `bench/rss-gate-results.json`. | CI — `pnpm rss-gate` |

|---|---|---|
| `ci-backend-images.sh` | Makes every image `docker-compose.yml` names local before the `integration` job starts it, one at a time through `lib/docker-pull.sh`, so each comes from the copy the Actions cache keeps or from a pull with backoff. ## The site

`site/` is published as-is, and these keep it true. See [`site/README.md`](../site/README.md).

| script | what it does | when |
|---|---|---|
| `site-figures.cjs` | Checks the site's money figures and its crossover rate against `bench/results.json`, `docs/benchmarks.md`, the latest calibration run's evidence in `bench/calibration/` and the pricing profile: every one must appear on `benchmarks.html`, which owns them, and a dollar amount that none of them accounts for fails on any of six site pages, `llms.txt`, the root and npm READMEs, the roadmap or `docs/benchmarks.md` — so no price can drift or improve without a run behind it. A run's figures pass at any honest precision, through the matcher its report is checked with, bindings included: wherever a paragraph, list item or table row states one of the run's figures or a request shape, every figure in it must also stand beside the words for the claim it makes. Inside `benchmarks.html`'s panel on the latest run, every unit and every count is checked, and each row against the run's derivation. The rate is required on `benchmarks.html` and its chart, and is checked wherever it stands in a block that quotes the run; stated anywhere else, it is not checked. Also: the measured values two pages quote — the RSS ceiling and soak figures on `benchmarks.html`, the encoding sizes on `flavors/roaring.html` — and any count of storage drivers on the pages or in `llms.txt`, against the drivers that ship, whether it says "drivers" or "backends". ## Conventions

- **Open with why.** Each script's header names the failure it prevents. A gate whose reason is lost gets deleted
  by the next person who finds it inconvenient.
- **Fail loudly.** A script that cannot do its job exits non-zero with a message saying what to do. A gate that
  silently passes when it cannot see its input is worse than no gate.
- **Verify a gate in both directions.** Plant the defect it exists for and watch it fail; then check that the
  legitimate look-alikes pass.
- **List it here.** `tests/docs/directory-readmes.test.ts` fails if a file in this directory has no row in a
  table here, or if a row names a file that does not exist.

## The images `consumer-install.cjs` runs in

`ci.yml` pins each Node image by the digest of its manifest list (the OCI index that names the amd64, arm64 and other
builds), as `node:<major>-bookworm@sha256:…`, and names three registries that serve it: `mirror.gcr.io/library`,
`public.ecr.aws/docker/library` and `docker.io/library`. A pull by digest returns the same image from whichever of them
answers, and fails if one serves something else, so a mirror cannot swap the image. The container runs as the numeric user
`1000:1000`, not a name looked up in the image's user table.

The digests were taken from Docker Hub, which is the source the mirrors copy: the `Docker-Content-Digest` header of
`HEAD /v2/library/node/manifests/<major>-bookworm`, sent with an `Accept` of
`application/vnd.oci.image.index.v1+json, application/vnd.docker.distribution.manifest.list.v2+json` and a token from
`auth.docker.io` for `repository:library/node:pull`. To refresh them, repeat that for `22-bookworm` and `24-bookworm`
(or run `docker buildx imagetools inspect node:22-bookworm` and read its `Digest:` line), put the new values in the
`matrix.include` of the `consumer-install` job in `.github/workflows/ci.yml` and in `DIGESTS` in
`tests/ci/consumer-install.test.ts`, and check that the job pulls from each registry. Nothing bumps them by itself, so
refresh them when a Node release or a Debian security fix matters to the check; until then it runs a fixed image.
