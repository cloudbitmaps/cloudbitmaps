# Calibration run `2026-09-23-94416`

**One real run against Amazon S3 in `us-east-1`, from a laptop 83 ms from the region, on 2026-09-23 (UTC).** It is
the first publishable run of the loaded store's calibration harness, and the first to measure what the
single-bucket design costs at a shape that tests it. In that design the registry pointer lives in the same bucket as
the data, so every pointer read and write is an S3 request on this bill. The harness had run against a real account
once before, also from a laptop. That run's shared ids fell into a handful of chunks, and most of its intersects
were answered from cache, so none of its figures are published; the harness was fixed before this run.

The evidence is [`2026-09-23-94416.json`](2026-09-23-94416.json), the results file the harness wrote, unedited. The
harness at commit `e42c27f` wrote it as `bench/calibrate-aws-results.json`, and it was moved here unchanged. That is
why its `note` still says to regenerate it: it predates the rule that a real run's evidence is written once, and a
new run now gets a new file.

Every dollar amount, percentage, duration, byte size, bit rate and ratio on this page, and every number written
before the request, chunk, id or load it counts, is checked against the evidence by
[`tests/docs/calibration-reports.test.ts`](../../tests/docs/calibration-reports.test.ts). So are the bill, the request
ledger and the table of cost by overlap, row by row. The check runs both ways: a headline figure missing from this
page fails it, and so does a figure the evidence cannot account for, or a right figure beside the words for another
claim, such as the expected intersect's cost called measured. [`bench/README.md`](../README.md#real-cloud-calibration) describes the
harness, and [`docs/benchmarks.md`](../../docs/benchmarks.md#real-cloud-calibration--aws) is where these figures are
published.

Every figure below is one of three kinds, and the text labels each one where it is first stated:

- **measured**: read straight from the evidence file;
- **derived**: measured request counts multiplied by the list prices in the library's default pricing profile
  (`aws-us-east-1-ondemand`: $0.40 per million GETs, $5 per million PUT-class requests, $0.023 per GiB-month), or
  other arithmetic over measured figures;
- **expected**: what the code predicts for a case this run did not measure. Each one names the parts it is built
  from.

Three terms recur:

- a **cold** intersect starts with nothing cached: a fresh store, which has read nothing yet;
- a **tail read** is a reader's first read of an object: its last 256 KiB, which holds the footer and the index;
- **PUT-class** requests are the ones S3 bills at the PUT rate: PUTs, a multipart upload's create, part and complete
  requests, and listings.

## 1. What one cold intersect does on S3

```
 a laptop ═════════ 83 ms a round trip ═════════▶  S3, us-east-1

 A ∩ B    two segments of 500,000 ids · 1,999 chunks each · 100 chunks in common

   pointer   A ── 1 GET ─────┐   first: which generation is current?      161 B each
             B ── 1 GET ─────┤
   tail      A ── 1 GET ─────┤   then: the last 256 KiB of the object,
             B ── 1 GET ─────┤   the footer and the whole index
   chunks    A ── 100 GETs ──┤   then: only the chunks both segments hold,
             B ── 100 GETs ──┘   516 B each on average
                             ──────────
                             204 GETs  →  $0.0000816 an intersect      expected
               this run: + 2 = 206 GETs  →  $0.0000824 an intersect      measured, the median
```

**Measured.** Every one of the 40 intersects returned exactly the planned ids, checked by count and by sum, and each
read 100 chunks per operand and one 256 KiB tail per operand.

**This run measured 206 GETs, not 204.** A store trusts a segment's pointer for 2 s (`cache.genTtlMs`, the default),
then reads it again on the next request, and that includes a request in the middle of an intersect. From the laptop
an intersect took about 3 s, so the median intersect read both pointers twice: 206 GETs. Inside the region an
intersect should finish well inside the 2 s and make 204 (**expected**, from the measured chunk and tail reads plus
one pointer read per operand).

A request count that moves with the network is a property of the network, so the harness no longer measures it that
way. Each timed intersect now pins its store's pointers (`cache.genTtlMs: 0`), so a cold intersect of this shape
counts 204 GETs wherever the client runs. A test drives the real engine on a clock where every storage read takes
three seconds: on the default refresh it reads the pointers again part-way through, and pinned it reads each one
once. What the 2 s refresh costs a long-lived reader is a separate figure, in
[what a cold intersect costs](#what-a-cold-intersect-costs-and-why).

## 2. Chunk-skipping on real S3

```
 segment A: each square is 20 chunks
 ■■■■■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 □□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 ■ fetched      100 chunks ·  5.0%
 □ skipped    1,899 chunks · 95.0%   never requested
```

**Measured.** An intersect fetched 100 of 1,999 chunks from each segment, 5.0% of them by count, and never requested
the other 1,899 chunks, 95.0% of the chunks. It knew which chunks could contribute from the two indexes alone. Until
this run, chunk-skipping at this shape had been shown only on local disk and on MinIO.

The 5.0% counts chunks. Counted in bytes, the chunk payload fetched is 4.9% of the two objects, a slightly smaller
share, because an object also holds its index and footer. The next section breaks the bytes down.

## 3. Bytes on the wire

One intersect, both operands:

```
 the two objects   ████████████████████████████████████████   2.10 MB   100%
 fetched           ████████████                               0.63 MB   29.8%
   tail reads      ██████████                                 0.52 MB   24.9%   fixed: 256 KiB per operand
   chunk reads     ██                                         0.10 MB    4.9%   grows with the overlap
 never left S3     ████████████████████████████               1.48 MB   70.2%

 and from objects of their own:
   pointer reads   ▏                                          0.6 KB            161 B a read
```

**Measured**: on average an intersect read 103,200 bytes of chunks and 524,288 bytes of tail, 627,488 bytes of the two
objects' 2,104,174 bytes, so 70.2% of the objects' bytes never left S3 (**derived**). The chunk reads sit at the front
of each object and the tail read at its end, so no byte is counted twice. It also read 611.8 bytes of pointers, 3.8
pointer reads of 161 bytes each. A pointer is an object of its own, so those bytes are in neither share.

**The object's size.** The harness recorded what each single-part load uploaded, 1,052,248 bytes, under the object's
name. That is the object plus the 161-byte body of its pointer. The object itself is 1,052,087 bytes, and every
figure on this page uses that. The harness now records the two apart.

**On a segment this small, the fixed tail read is most of what is fetched.** The reader takes the last 256 KiB of
each object in one request, so the footer and the whole index arrive in a single round trip. For a 1.05 MB segment
that is a quarter of the bytes. On a segment a hundred times larger it would be noise. Inside the region S3 bills a
read by the request, not by the byte, so there the tail read changes the bytes moved and not the bill; read from
outside the region, as this run was, its bytes are transfer out, billed by the gigabyte (below).

**The tail read also carries payload.** On a segment this small, the last 256 KiB reaches back past the index into
the chunks: 242,049 bytes of payload, about 469 chunks' worth, which the intersect downloads with the index and never
uses. It requests only the chunks it needs, but not every byte it downloads belongs to one of them. That is
**derived**, from the index size below.

**How big a segment the tail read covers.** Each chunk is stored in
[roaring's portable format](https://github.com/RoaringBitmap/RoaringFormatSpec), which writes a chunk of up to 4,096
ids as a 16-byte header and 2 bytes an id. That predicts 51,600 bytes for the 100 chunks each operand read, exactly
what the run measured. It also puts each segment's payload at 1,031,984 bytes. Take that, the 8-byte preamble and
the 104-byte footer from the 1,052,087-byte object, and 19,991 bytes are left for the index: 10.0 bytes a chunk. At
that rate a 256 KiB tail holds the index of a segment spanning up to about 26,000 chunks. That is **derived**, and it
varies a little with chunk size. What an intersect costs when an index outgrows the tail is in
[what a cold intersect costs](#what-a-cold-intersect-costs-and-why).

## 4. Loading data

```
 a 1.05 MB segment, one PUT                 a 12.6 MB segment, multipart
   GET  the pointer   the loader's check      GET  the pointer   the loader's check
   PUT  the new generation                    create the upload
   GET  the pointer   the publish             upload a part, twice
   GET  the pointer   the registry            complete the upload
   PUT  the pointer, only if still absent     GET  the pointer   the publish
                                              GET  the pointer   the registry
                                              PUT  the pointer, only if still absent
   = 2 PUT + 3 GET                            = 5 PUT-class + 3 GET
```

**Measured**:

- 22 `PutObject`s: 10 single-part generations, then one pointer for each of the 12 loads;
- for each of the 2 multipart loads, a create, 2 parts and a complete;
- 36 `GetObject`s that returned no bytes, 3 for each of the 12 loads.

The meter sorts only the reads that return bytes, so the 36 are found by subtraction: 8,268 `GetObject`s in all, less
the 152 pointer reads, 80 tail reads and 8,000 chunk reads that returned bytes. Every segment was new, so each of
the 36 found no pointer and answered 404.

**Why a load reads the pointer three times.** The loader reads the segment's row once before it writes: a check, to
refuse a destroyed segment and to reuse an encrypted one's key. The publish step reads it again at the top of its
compare-and-swap loop. The registry reads it once more before its conditional write, to find a deleted row's
tombstone, so that a re-created segment never reuses an old token. At $0.40 per million GETs, all three together
cost $1.20 per million loads. That is 11% of the bill for a write and publish; the two PUTs are the other $10
(**derived**).

Before the single-bucket design, the pointer lived in a NoSQL table, and its reads and its write never appeared in
the S3 figures. Here they are part of the bill.

**What was measured is the write and the publish.** The harness calls `bulkLoadCrbmGeneration` with the generation
number given. `store.load()`, the one-call load the guide leads with, does more. A test counts its requests against
local drivers and the real registry code:

- it lists the segment's objects to choose the next generation number, and lists them again for a collection pass
  after the publish;
- it reads the pointer four more times on a segment's first two loads, and five more from the third on, when the
  collection pass has a generation to delete and re-reads the pointer before it;
- a reload also reads the current generation's index, to count what the load replaces.

A listing bills at the PUT rate. So a segment's first `store.load()` is 4 PUT-class and 7 GET requests, $22.80 per
million; a reload is 4 and 8, $23.20; and from the third load on it is 4 and 9, $23.60, plus a delete, which is
free. That is about twice the write and publish. These are **expected**: the counts are tested, and the next run
should measure them on S3.

## 6. Why the latency and upload figures are not the library's

```
 laptop ════ 83 ms a round trip ════ S3, us-east-1

 the median intersect   2,912 ms, about 35 times the round-trip floor
   waiting in line      about 16 requests: a pointer read, a tail read, 100 shared chunks
                        read 8 at a time in about 13 rounds, and one pointer re-read    expected
   each one             about 182 ms, more than twice the round-trip floor              derived

 a single-part load     721 KB/s = 5.8 Mbit/s: its bytes over the whole call
 a multipart load       1.41 MB/s = 11 Mbit/s, over the same connection
```

**Measured, and not the library's figures:**

- the intersect's p50 was 2,912 ms, its p95 4,189 ms and its p99 4,193 ms. With 40 samples, the p99 is simply the
  slowest intersect and the p95 the second slowest;
- single-part loads ran at 721 KB/s and multipart loads at 1.41 MB/s.

**The intersect.** 2,912 ms is about 35 times the 83 ms floor, but that is not a line of round trips 35 deep. The
engine reads each operand's pointer and then its tail, both operands at once. It then keeps 8 shared chunks in flight,
reading each from both operands at once, so 100 shared chunks take about 13 rounds. And the median intersect outlived
the 2 s refresh, so part-way through it read both pointers again, and every chunk read that started meanwhile waited
for that. That puts about 16 requests in line, each waiting for the one before (**expected**, from the engine's
code); with each pointer read once, as inside the region, it would be 15 requests. Spread over the 16, each took about
182 ms, more than twice the floor. The run does not say where the rest went. S3's own time to
answer and the connections the client opened on the way are both candidates, and inside the region both would sit on
a far shorter round trip.

**The uploads.** 721 KB/s is 5.8 Mbit/s, but it is not the uplink's speed: the multipart loads crossed the same
connection at 1.41 MB/s, 11 Mbit/s. A load's rate divides its bytes by the whole call. That includes building the
object, then five requests one after another: a pointer read, the object's PUT, two more pointer reads and the
pointer's PUT. At 83 ms a round trip, those five take at least 0.42 s of the 1.46 s a median single-part load took.
A multipart load, with twelve times the bytes, spreads the same kind of wait over a larger object.

Inside the region a round trip is a small fraction of 83 ms, so the same intersect should take a small fraction of
the time. That is **expected**, not measured, and how small a fraction is exactly what the in-region run is for.
Measuring it takes a run from inside the region: `bash bench/calibrate-cloudshell.sh` in AWS CloudShell,
[described here](../README.md#running-it-in-the-region).

## What a cold intersect costs, and why

**$82.40 is the price of a million cold intersects. One costs $0.0000824, less than a hundredth of a cent**: a dollar
buys 12,135 cold intersects of this shape (**derived**).

```
 GETs per cold intersect  =  2 pointer reads  +  2 tail reads  +  2 × (chunks the two segments share)
                             └───────────── 4 ──────────────┘     └──── grows with the overlap ─────┘
                             while each index fits the tail read

 expected:  4 + 2 × 100  =  204 GETs  ×  $0.0000004 a GET  =  $0.0000816 an intersect, $81.60 a million
 measured:  the median made 206, two more pointer reads     =  $0.0000824 an intersect, $82.40 a million
```

Three things follow from that formula.

- **What a cold intersect costs depends on how much the two segments overlap, not on how big they are**, while each
  index fits the tail read: up to about 26,000 chunks of this shape. Two such segments cost 4 + 2k GETs for k
  shared chunks, whatever their size. Only the bytes moved differ, and inside the region S3 bills a read by the
  request.
- **This run measured the worst case, on purpose.** Every intersect started from an empty cache.
- **A segment whose index outgrows the tail read costs one more GET**, which reads its whole index: 5 + 2k when one
  operand is that large, and 6 + 2k when both are.

**Expected**, from the run's request shape, with each pointer read once:

| chunks the two share | GETs | one intersect | a million | per dollar |
|---:|---:|---:|---:|---:|
| 1 | 6 | $0.0000024 | $2.40 | 416,666 |
| 10 | 24 | $0.0000096 | $9.60 | 104,166 |
| **100 (the run's overlap)** | **204** | **$0.0000816** | **$81.60** | **12,254** |
| 1,000 | 2,004 | $0.0008016 | $801.60 | 1,247 |
| 1,999 (identical segments) | 4,002 | $0.0016008 | $1,600.80 | 624 |

**Is that good? Per query it is very cheap. What matters is volume**, compared with keeping a node running all
month. The Redis-HA line is $346 a month whether or not it is used. That buys 4.2 million cold intersects a month of
this shape as the run measured it, 1.6 a second around the clock; at 10 shared chunks it would buy 36.0 million,
13.7 a second (**expected**). Below those rates this design is the cheaper one; above them, a standing node is. The benchmarks page
publishes the same crossover for point reads, and says so in the same terms.

**A long-lived reader pays less, and one more thing** (**expected**, from the code; not measured here):

- A store that stays up answers a repeat intersect from memory: the chunks, the index and the resolved pointer are
  all cached.
- What it keeps paying is the pointer refresh: at most one GET per segment every 2 s while the segment is being read.
  For a segment read around the clock, that is $0.53 a month at the default refresh.
- Raising `cache.genTtlMs` lowers that cost, at the price of a new load taking longer to become visible.

## Great, or just average?

**The library's own figures are great:**

- 95.0% of the chunks skipped on real S3, with all 40 intersects exact;
- $82.40 per million cold intersects of two 500,000-id segments as the run measured them, and $81.60 expected with
  each pointer read once;
- $11.20 per million writes and publishes, the pointer included, and for a segment's first `store.load()` an
  expected $22.80;
- the $346-a-month Redis line buys 4.2 million cold intersects of this shape.

**The average-looking numbers are not the library's.** The 2.9 s intersects and the 721 KB/s uploads measured a
laptop 83 ms from the region. They are recorded here and stated nowhere else. No sample was dropped or picked to
flatter them: each figure covers every intersect or every load the run timed. A great latency figure needs the run
to happen where the library runs, which is the in-region run.

**Levers that would make the library's numbers better still**, in the order they pay:

1. **Fetch neighbouring chunks together.** Chunk reads are 200 of the median intersect's 206 GETs, 97% of its bill
   (**derived**).
   Coalescing nearby chunks into fewer, larger ranged GETs could cut that sharply, at the cost of downloading some
   bytes no one asked for. It changes the hot path, so it needs a design, and measurements, before any code.
2. **Size the tail read to the segment.** A tail sized to the index moves fewer bytes on small segments. It does not
   change the bill inside the region, where S3 bills a read by the request.
3. **Fold a load's pointer reads.** After the loader's check, two more GETs re-read the pointer before the
   compare-and-swap. They fence races, though, and the most they could save is $0.80 per million loads
   (**derived**).

**The estimator got the same correction the bill got.** When this run was published, `estimateCost()` priced a load
as its object's PUT-class requests alone, with no term for the pointer's PUT or its GETs, and an intersect as its
chunk reads alone, with no term for the pointer and tail reads; it had no term for the pointer refresh either. It
now counts all three, each held by a test to the requests the engine makes: a cold intersect of this shape at the
expected 204 GETs, a load at what `store.load()` makes around its object's write, and the refresh for the segments
a reader keeps reading.

## What this run does not establish

- **Latency or throughput.** The client was 83 ms from the region; see [section 6](#6-why-the-latency-and-upload-figures-are-not-the-librarys).
- **What `store.load()` costs on S3.** The run measured the write and the publish. A test counts what
  `store.load()` adds; see [section 4](#4-loading-data).
- **Other shapes.** It measured one: two operands, 100 of 1,999 chunks shared. Not more operands, not other overlaps,
  not `andNot` with an `exclude`, not the `*Into` verbs.
- **Lambda.** A function's cold start and initialisation are a separate figure, and need a run from inside one.
- **The invoice.** These are list prices applied to request counts metered at the SDK, not AWS's bill.
- **Data transfer.** 25.1 MB came back to the laptop and 35.8 MB went up. The harness counts those bytes, and prices
  only the requests.
  Uploads into S3 are free, and so is anything read from inside the region. Reading out to the internet, as this
  laptop did, is billed per gigabyte, and at 25.1 MB it comes to a fraction of a cent.

## Where this run sits

On the [roadmap](../../docs/ROADMAP.md#on-the-way-to-10), `1.0` waits on real-cloud calibration, of cost and of
in-region latency, among other things. This run pays the cost side for the topology that ships: the request shape of
a cold intersect and of a load's write and publish, and what each costs, with the pointer in the bill. The benchmarks
page keeps the one list of [what is still owed](../../docs/benchmarks.md#what-is-still-owed). This run leaves on it:

- in-region intersect latency and load throughput, which a run from CloudShell measures;
- in-region point-read latency, and `andNot`, the `*Into` verbs and the sweep over operand count and overlap, which
  the harness does not measure yet;
- what `store.load()` costs, measured on S3;
- the Lambda figure.
