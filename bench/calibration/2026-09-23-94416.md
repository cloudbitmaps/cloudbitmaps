# Calibration run `2026-09-23-94416`

**One real run against Amazon S3 in `us-east-1`, from a laptop 83 ms from the region, on 2026-09-23.** It is the
first run of the loaded store's own calibration harness against a real account, and the first measurement of what
the single-bucket design costs: the registry pointer now lives in the same bucket as the data, so every pointer
read and write is an S3 request on this bill.

The evidence is [`2026-09-23-94416.json`](2026-09-23-94416.json), the results file the harness wrote, unedited.
Every dollar amount, percentage, duration and byte size on this page is checked against it by
[`tests/docs/calibration-reports.test.ts`](../../tests/docs/calibration-reports.test.ts). The check runs both
ways: a headline figure missing from this page fails it, and so does a figure the evidence cannot account for.
[`bench/README.md`](../README.md#real-cloud-calibration) describes the harness, and
[`docs/benchmarks.md`](../../docs/benchmarks.md#real-cloud-calibration--aws) is where these figures are published.

Every figure below carries one of three labels:

- **measured**: read straight from the evidence file;
- **derived**: measured request counts multiplied by the list prices in the library's default pricing profile
  (`aws-us-east-1-ondemand`: $0.40 per million GETs, $5 per million PUT-class requests, $0.023 per GiB-month);
- **expected**: what the code predicts for a case this run did not measure. Each one names the measured parts it
  is built from.

## At a glance

The run produced three kinds of result.

1. **Proof, on real S3, that the core idea works.** 40 of 40 cold intersects returned exactly the right ids, and
   each fetched 100 of 1,999 chunks per segment: the 100 the two segments share, and nothing else.
2. **The single-bucket bill.** A cold intersect of this shape is 204 GETs, $0.0000816 each, or $81.60 for a
   million of them. A load is 2 PUTs and 3 GETs, $11.20 per million; a multipart load is $26.20 per million. The
   whole run cost $0.0034816.
3. **Latency and upload figures that measured the laptop's connection, not the library.** They are recorded
   below with the reason, and are not published as the library's.

## 1. What one cold intersect does on S3

```
 a laptop ═════════ 83 ms a round trip ═════════▶  S3, us-east-1

 A ∩ B    two segments of 500,000 ids · 1,999 chunks each · 100 chunks in common

   ① pointer   A ── 1 GET ───┐   "which generation is current?"         161 B each
               B ── 1 GET ───┤
   ② index     A ── 1 GET ───┤   the last 256 KiB of the object:
               B ── 1 GET ───┤   footer and index in one round trip
   ③ chunks    A ── 100 GETs ┤   only the chunks both segments have,
               B ── 100 GETs ┘   516 B each
                             ──────────
                             204 GETs   →   $0.0000816 per intersect
```

**Measured.** Every one of the 40 intersects returned exactly the planned ids, checked by count and by sum, and
each read 100 chunks per operand and one 256 KiB tail per operand.

**This run measured 206 GETs, not 204.** A store trusts a segment's pointer for 2 s (`cache.genTtlMs`, the
default), then reads it again on the next request, and that includes a request in the middle of an intersect.
From the laptop an intersect took about 3 s, so the median intersect read both pointers twice: 206 GETs. Inside
the region an intersect finishes well inside the 2 s, so it makes 204 (**expected**, from the measured chunk and
tail reads plus one pointer read per operand).

A request count that moves with the network is a property of the network, so the harness no longer measures it
that way. Each timed intersect now pins its store's pointers (`cache.genTtlMs: 0`), and a cold intersect of this
shape counts 204 GETs wherever the client runs. A test drives the real engine on a clock where every storage read
takes three seconds: on the default refresh it reads the pointers again part-way through, and pinned it reads each
one once. What the 2 s refresh costs a long-lived reader is a separate figure, in
[what a cold intersect costs](#what-a-cold-intersect-costs-and-why).

## 2. Chunk-skipping on real S3

```
 segment A: each square is 20 chunks
 ■■■■■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 □□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 ■ fetched      100 chunks ·  5.0%
 □ skipped    1,899 chunks · 95.0%   never requested
```

**Measured.** An intersect fetched 100 of 1,999 chunks from each segment, 5.0% of them by count, and skipped the
other 1,899 chunks, 95.0%. It knew which chunks could contribute from the two indexes alone. Until this run, that
had been shown only on local disk and on MinIO.

The 5.0% counts chunks. Counted in bytes, the chunk payload fetched is 4.9% of the two objects, a slightly
smaller share, because an object also holds its index and footer. The next section breaks the bytes down.

## 3. Bytes on the wire

One intersect, both operands:

```
 the two objects   ████████████████████████████████████████   2.10 MB   100%
 fetched           ████████████                               0.63 MB   29.8%
   tail reads      ██████████                                 0.52 MB   24.9%   fixed: 256 KiB per operand
   chunk reads     ██                                         0.10 MB    4.9%   grows with the overlap
   pointers        ▏                                          0.6 KB
```

**Measured**: 103,200 bytes of chunks, 524,288 bytes of tail and 0.6 KB of pointers, out of 2,104,496 bytes in
the two objects. So 70.2% of the objects' bytes never left S3.

**On a segment this small, the fixed tail read is most of what is fetched.** The reader takes the last 256 KiB of
each object in one request, so the footer and the whole index arrive in a single round trip. A 1.05 MB segment
makes that a quarter of the bytes. On a segment a hundred times larger it would be noise. S3 bills per request,
not per byte, so the tail changes the bytes moved and not the bill.

**How big a segment the tail read covers.** Here the index is about 10 bytes a chunk. Each chunk is stored in
[roaring's portable format](https://github.com/RoaringBitmap/RoaringFormatSpec), which writes a chunk of up to
4,096 ids as a 16-byte header and 2 bytes an id. That predicts 51,600 bytes for the 100 chunks each operand read,
exactly what the run measured. It
also puts each segment's payload at 1,031,984 bytes, which leaves 20,152 bytes of index in a 1,052,248-byte
object. At about 10 bytes a chunk, a 256 KiB tail holds the index of a segment spanning up to about 26,000
chunks. That is **derived**, and it varies a little with chunk size. A segment spread over more chunks takes one
more GET per operand to finish reading its index, so its fixed cost is 6 GETs instead of 4.

## 4. Loading data

```
 a 1.05 MB segment, one PUT               a 12.6 MB segment, multipart
   GET  the pointer        (the loader)     GET  the pointer        (the loader)
   PUT  the new generation                  create the upload
   GET  the pointer        (the publish)    upload part × 2
   GET  the pointer        (the registry)   complete the upload
   PUT  the pointer, only if still absent   GET  the pointer × 2    (the publish, the registry)
                                            PUT  the pointer, only if still absent
   = 2 PUT-class + 3 GET                    = 5 PUT-class + 3 GET
```

**Measured**:

- 22 `PutObject`s: 10 single-part generations, then one pointer for each of the 12 loads;
- 2 × (create, 2 parts, complete) for the multipart loads;
- 36 pointer reads that found nothing, 3 for each of the 12 loads.

Every segment was new, so each of those reads answered 404. That is why they appear in the request counts and
not among the reads that returned bytes.

**Why a load reads the pointer three times.** The loader reads the segment's row before it writes, to refuse a
destroyed segment and to reuse an encrypted one's key. The publish step reads it again inside its
compare-and-swap loop. The registry reads it once more before its conditional write, to check for a deleted
row. Each re-read is a fence against a concurrent writer, and at $0.40 per million GETs, all three together cost
$1.20 per million loads. That is 11% of a load's bill; the two PUTs are the other $10.

Before the single-bucket design, the pointer lived in a NoSQL table, and its reads and its write never appeared
in the S3 figures. Here they are part of the bill.

**What was measured is the write and the publish.** The harness calls `bulkLoadCrbmGeneration` with the
generation number given. `store.load()`, the one-call load the guide leads with, does more:

- it lists the segment's objects to choose the next generation number;
- after the publish, it runs a collection pass that lists them again;
- it reads the pointer four more times.

Listings bill at the PUT rate, so a load through `store.load()` should cost roughly twice the figure above. That
is **expected**, from the code, and not measured. The next run should measure `store.load()` itself.

## 6. Why the latency and upload figures are not the library's

```
 laptop ════ 83 ms a round trip ════ S3     median intersect 2,912 ms ≈ 35 round trips of waiting
 upload 721 KB/s ≈ 5.8 Mbit/s               the laptop's uplink, not S3
 inside the region                          the same ~35 round trips, each a fraction of 83 ms
                                            → expected: a fraction of the time. Not measured.
```

**Measured, and not the library's figures:**

- the intersect's p50 was 2,912 ms, its p95 4,189 ms and its p99 4,193 ms. With 40 samples, the p99 is simply the
  slowest intersect and the p95 the second slowest;
- single-part loads ran at 721 KB/s and multipart loads at 1.41 MB/s.

At 83 ms a round trip, 2,912 ms is about 35 round trips of waiting, and 721 KB/s is 5.8 Mbit/s, the speed of the
laptop's uplink. These numbers describe the distance between the laptop and the region.

Inside the region a round trip is a small fraction of 83 ms, so the same intersect should take a small fraction of
the time. That is **expected**, not measured, and how small a fraction is exactly what the in-region run is for.
This page publishes no latency and no throughput. Measuring them takes a run from inside the region: `bash bench/calibrate-cloudshell.sh` in AWS
CloudShell, [described here](../README.md#running-it-in-the-region).

## What a cold intersect costs, and why

**$81.60 is the price of a million intersects. One costs $0.0000816, about a hundredth of a cent.**

```
 GETs per cold intersect  =  2 pointer reads  +  2 tail reads  +  2 × (chunks the two segments share)
                             └──────── 4, whatever the size ───────┘   └────── grows with the overlap ──────┘

 this run:  4 + 2 × 100  =  204 GETs  ×  $0.0000004 a GET  =  $0.0000816 an intersect
                                                              ($81.60 for a million of them)
```

Three things follow from that formula.

- **What a cold intersect costs depends on how much the two segments overlap, not on how big they are.** Two
  segments of any size whose indexes fit the tail read, up to about 26,000 chunks each, cost 4 + 2k GETs for k
  shared chunks. Only the bytes moved differ, and S3 bills per request.
- **This run measured the worst case, on purpose.** Every intersect started from an empty cache.
- **A segment spread over more chunks than the tail holds costs two more GETs**, one per operand, for the rest of
  its index: 6 + 2k.

| chunks the two share | GETs | one intersect | a million | per dollar |
|---:|---:|---:|---:|---:|
| 1 | 6 | $0.0000024 | $2.40 | 416,667 |
| 10 | 24 | $0.0000096 | $9.60 | 104,167 |
| **100 (this run)** | **204** | **$0.0000816** | **$81.60** | **12,255** |
| 1,000 | 2,004 | $0.0008016 | $801.60 | 1,248 |
| 1,999 (identical segments) | 4,002 | $0.0016008 | $1,600.80 | 625 |

**Is that good? Per query, it is very cheap. What matters is volume**, compared with keeping a node running all
month. The Redis-HA line is $346 a month whether or not it is used. That buys 4.2 million cold intersects a month
of this shape, 1.6 a second around the clock, or 36.0 million at 10 shared chunks, 13.7 a second. Below those
rates this design is the cheaper one; above them, a standing node is. The benchmarks page publishes the same
crossover for point reads, and says so in the same terms.

**A long-lived reader pays less, and one more thing** (**expected**, from the code; not measured here):

- A store that stays up answers a repeat intersect from memory: the chunks, the index and the resolved pointer are
  all cached.
- What it keeps paying is the pointer refresh: at most one GET per segment every 2 s while the segment is being
  read. For a segment read around the clock, that is $0.53 a month at the default refresh.
- Raising `cache.genTtlMs` lowers that cost, at the price of a new load taking longer to become visible.

## Great, or just average?

**The library's own figures are great:**

- 95.0% of the chunks skipped on real S3, with 40 of 40 intersects exact;
- $81.60 per million cold intersects of two 500,000-id segments;
- $11.20 per million loads, the pointer included;
- the $346-a-month Redis line buys 4.2 million cold intersects of this shape.

**The average-looking numbers are not the library's.** The 2.9 s intersects and the 721 KB/s uploads measured the
laptop's internet connection. They are recorded here and published nowhere else, and no sample was picked to
flatter them: every figure on this page is one the run produced. A great latency figure needs the run to happen
where the library runs, which is the in-region run.

**Levers that would make the library's numbers better still**, in the order they pay:

1. **Fetch neighbouring chunks together.** Chunk reads are 200 of the 204 GETs, 98% of an intersect's bill.
   Coalescing nearby chunks into fewer, larger ranged GETs could cut that sharply, at the cost of downloading
   some bytes no one asked for. It changes the hot path, so it needs a design, and measurements, before any code.
2. **Size the tail read to the segment.** A tail sized to the index moves fewer bytes on small segments. It does
   not change the bill, since S3 bills per request.
3. **Fold a load's pointer reads.** Two of a load's three GETs re-read what the first one read. They fence races,
   though, and the most they could save is $0.80 per million loads.

**The estimator needs the same correction the bill got.** `estimateCost()` prices a load as `requestsPerLoad`
PUT-class requests, 1 by default. That is $5 per million loads, against the $11.20 measured here, because it has
no term for the pointer's PUT and GETs. It prices an intersect as `chunksPerIntersect` GETs; this shape makes 204.
Until the estimator counts both itself, price a single-bucket load at $11.20 per million, and pass
`chunksPerIntersect: 204` for an intersect of this shape.

## What this run does not establish

- **Latency or throughput.** The client was 83 ms from the region; see [section 6](#6-why-the-latency-and-upload-figures-are-not-the-librarys).
- **What `store.load()` costs.** The run measured the write and the publish, not the generation listing and
  collection pass around them; see [section 4](#4-loading-data).
- **Other shapes.** It measured one: two operands, 100 of 1,999 chunks shared. Not more operands, not other
  overlaps, not `andNot` with an `exclude`, not the `*Into` verbs.
- **Lambda.** A function's cold start and initialisation are a separate figure, and need a run from inside one.
- **The invoice.** These are list prices applied to request counts metered at the SDK, not AWS's bill.
- **Data transfer.** 25.1 MB came back to the laptop and 35.8 MB went up. The harness meters requests, not
  transfer. Uploads into S3 are free, and so is anything read from inside the region. Reading out to the
  internet, as this laptop did, is billed per gigabyte, and at 25.1 MB it comes to a fraction of a cent.
