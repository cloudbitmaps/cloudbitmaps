# Calibration run `2026-10-06-9d36b`

**One real run against Amazon S3 in `us-east-1`, from AWS CloudShell in the same region, on 2026-10-06 (UTC), against
the published `0.17.0`.** It is the fifth complete in-region run, and the first with the steady-load stage: one
segment loaded 18 loads at `keep: 12`, each load's requests recorded by kind. Its client sat 4.50 ms from S3, so its latencies and load rates are the library's,
not a network's. It measures load throughput, cold intersect latency, point reads, `andNot` and a steady `store.load()` on the single-bucket
design, and the bill for all of it. The earlier runs, [`2026-10-03-e13c7`](2026-10-03-e13c7.md),
[`2026-10-04-73668`](2026-10-04-73668.md), [`2026-10-04-f3599`](2026-10-04-f3599.md) and
[`2026-10-05-50b5d`](2026-10-05-50b5d.md), measured earlier releases and stay as the record of them. Every stage
that run timed made the same requests here. Latencies of runs from different CloudShell sessions are not comparable,
so this report sets none against another's.

The evidence is [`2026-10-06-9d36b.json`](2026-10-06-9d36b.json), the results file the harness wrote, unedited. Every
dollar amount, percentage, duration, byte size and ratio on this page, and every number written before the request,
chunk, id or load it counts, is checked against the evidence by
[`tests/docs/calibration-reports.test.ts`](../../tests/docs/calibration-reports.test.ts). So are the bill and the
request ledger, row by row. [`bench/README.md`](../README.md#real-cloud-calibration) describes the harness, and
[`docs/benchmarks.md`](../../docs/benchmarks.md#real-cloud-calibration--aws) is where these figures are published.

Every figure below is one of three kinds, and the text labels each one where it is first stated:

- **measured**: read straight from the evidence file;
- **derived**: measured request counts multiplied by the list prices in the library's default pricing profile
  (`aws-us-east-1-ondemand`: $0.40 per million GETs, $5 per million PUT-class requests, $0.023 per GiB-month), or
  other arithmetic over measured figures;
- **expected**: what the library's code and its tests predict, not something this run counted.

Four terms recur:

- a **cold** intersect starts with nothing cached: a fresh store, which has read nothing yet;
- a **tail read** is a reader's first read of an object: its last 256 KiB, which holds the footer and the index;
- a **range read** is one request for a stretch of an object's bytes, which holds every shared chunk that lies within
  256 KiB of the one before it, up to 1 MiB;
- **PUT-class** requests are the ones S3 bills at the PUT rate: PUTs, a multipart upload's create, part and complete
  requests, and listings.

## Chunk-skipping on real S3

```
 segment A: each square is 20 chunks
 ■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 □□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 ■ read as ONE range      the 100 shared chunks, 5.0% of the chunks
 □ never requested      1,899 chunks · 95.0%
```

**Measured.** An intersect read each operand's 100 shared chunks as a single range request, and never requested the
other 1,899 chunks, 95.0% of the chunks. It knew which chunks could contribute from the two indexes alone, as the
earlier runs' did. It fetched 100 of 1,999 chunks from each segment, 5.0% of them by count. The 100 chunks are not
each a request, because they lie together and one range holds them all.

The 5.0% counts chunks. Counted in bytes, the chunk payload fetched is 4.9% of the two objects, a slightly smaller
share, because an object also holds its index and footer, and the 256 KiB tail read at the end of each one is
fixed.


| | single-part | multipart |
|---|---|---|
| loads | 20 | 5 |
| the object | 1,052,088 bytes | 12,622,960 bytes |

- A single-part load of 500,000 ids took about 193 ms, and a multipart load of 12,582,912 ids about 1.83 s

- Each load uploaded 274 to 277 bytes more than its object: the pointer's body, which is not part of the object.

- A load's rate divides its bytes by the whole call. That includes building the object, then the loader's reads and

## 2. Cold intersect latency

```
 A ∩ B    two segments of 500,000 ids · 1,999 chunks each · 100 chunks in common

   pointer   A ── 1 GET ─────┐
             B ── 1 GET ─────┤
   tail      A ── 1 GET ─────┤   the last 256 KiB of each object
             B ── 1 GET ─────┤
   chunks    A ── 1 GET ─────┤   one range: the 100 shared chunks
             B ── 1 GET ─────┘
                             ──────────
                             6 GETs  →  $0.0000024 an intersect
```

**Measured**, 40 cold intersects each:

| layout | p50 | p95 | p99 | GETs | rounds |
|---|---|---|---|---|---|
| the shared chunks packed together | 99.80 ms | 120.32 ms | 141.24 ms | 6 | 3.9 |
| the shared chunks spread across the segment | 103.06 ms | 161.99 ms | 164.10 ms | 6 | 4.0 |

- Every intersect returned exactly the planned ids, checked by count and by sum, and read one range and one tail
  per operand. The median made 6 GETs: 2 pointer reads, 2 tail reads and 2 range reads. Each pointer was read
  once, because an intersect finished well inside the 2 s pointer refresh. Nothing was off the expected count, and
  the harness turned the pointer refresh off for the timed intersects (`cache.genTtlMs: 0`), so the count does not
  move with the network.
- With 40 samples, the p99 is the slowest intersect and the p95 the second slowest.
- The spread layout also took 6 GETs: its shared chunks lie across each object, and the engine joined them into one
  range anyway. Each range read returned 1,022,196 bytes of an operand (**derived**: the stage's range bytes over its range
  requests), because the bytes between the chunks come with them. The packed layout's range returned 51,600 bytes.
- A cold intersect is the worst case for this design: nothing cached, every byte from S3.

### Rounds

The engine reads each operand's pointer, then its tail, both operands at once. It then reads the shared chunks of
each operand as one range, both operands at once. That makes a model of 3 requests in line, each waiting for the one
before (**expected**, from the engine's code, the rounds model, which assumes no limit on open sockets). The run
measured 3.9 rounds for the packed layout and 4.0 for the spread one: the median's mean in-flight requests, divided
into its total request time, so a round is a request's duration averaged over everything in flight (the harness's own
figure; the model is not tuned to it). The measured depth is above the rounds model's: 3.9 against 3, and the spread
layout's 4.0.

**The measured rounds are above the rounds model, and the run does not say why.** The client had 128 sockets, and
the model assumes no socket limit. The packed intersect's median peaked at 2 in flight and held a mean of 1.6 (the
spread layout's, 1.5), so a socket limit did not bind. The gap is a finding and is not tuned away. The run did not vary
the socket count.

**A GET round is about 25 to 30 ms in this run** (**derived**: p50 ÷ measured rounds, 99.80 ms ÷ 3.9 = 25.7 ms, and
25.5 ms for the spread layout; the sweep below gives 26.5 and 25.1, and the `andNot` 30.2). That is more than the
round-trip floor of 4.50 ms. The run does not say why: S3's own time to first byte and the client's connection
handling are both candidates, and so is the time to read a range of up to 1 MiB.

## 3. How a cold intersect grows with the overlap

The same intersect at more shared chunks, `k`, each on a fresh store (**measured**):

| shared chunks | intersects | p50 | p95 | GETs | rounds | model |
|---|---|---|---|---|---|---|
| 1,000 | 10 | 197.74 ms | 372.75 ms | 6 | 7.5 | 3 |
| 2,000 | 5 | 304.28 ms | 366.75 ms | 6 | 12.1 | 3 |

- Doubling `k` did not change the GETs: 6 at both. The shared chunks lie together, so each operand's are one range
  however many there are. The p50 went from 197.74 ms to 304.28 ms, 1.54 times (**derived**), for twice the chunks:
  the requests stayed the same and each carried more bytes.
- With 10 and 5 samples, the p95 is the slowest or the second slowest intersect and says little by itself.
- The rounds again run above the rounds model's: 7.5 against 3 and 12.1 against 3. At these in-flight depths, 0.8 and
  0.5 on average, the run does not say why.

## 4. Warm intersect, point reads and `andNot`

**Warm intersect** (**measured**, 40 intersects on a store that had read both segments already): p50 7.32 ms, p95
10.84 ms and p99 10.92 ms, with no request at all. Answering from memory is a few milliseconds; the work is merging
the chunks.

**Point reads** (**measured**, 10 segments):

| read | requests | p50 | p95 |
|---|---|---|---|
| `count()`, cold | 1 | 27.19 ms | 29.17 ms |
| `has()`, opening the segment | 1 | 26.45 ms | 31.26 ms |
| `has()`, on an open segment, first read of a chunk | 1 | 26.10 ms | 33.42 ms |
| `has()`, first read of an id on a store with the pointer refresh off | 3 | 78.99 ms | 105.95 ms |
| `count()`, warm | 0 | 0.0053 ms | 0.0090 ms |
| `has()`, warm | 0 | 0.0075 ms | 0.0109 ms |

- A cold `count()` is one request: the cardinality is in the pointer's row, so it opens nothing. Its 27.19 ms is one
  GET round.
- A `has()` on an open segment is one chunk GET, one round. The first read on a store that had to read the pointer,
  the tail and then the chunk is three requests, three rounds, 78.99 ms.
- A warm read never leaves memory: under 10 microseconds at the median.

**`andNot`** (**measured**, 10 calls, each of a 1,999-chunk segment with 10 excludes): p50 351.64 ms, p95
461.51 ms and p99 461.51 ms. Each call made 33 GETs: 11 range reads, 11 tail reads and 11 pointer reads, with a mean
in flight of 3.0 and up to 11 at the peak. Each operand, the include and the ten excludes, had its pointer and
tail read and its chunks read as one range; the rounds were 11.7.

## 5. A steady load

```
 one small segment, a different set of ids each generation, loaded 18 loads with store.load() at keep: 12

 generation   0       1 ... 12        13  14  15       16         17
 kind         first   reload (12)     by name (3)      listing    by name
 requests     2+3     2+2             2+4 and a delete 3+5 and    2+4 and a
                                                       a delete   delete
              (PUT-class + GET-class)
```

The stage runs last, on a store of its own, and records each load's requests by class, its bytes and its time. Each
load is held to the requests of its kind, which the harness counts by running the engine over the in-memory backend:

- **first**: the segment's first load, which finds no row.
- **reload**: a load of generations 1 to 12, whose window still holds every earlier generation, so it collects
  nothing.
- **by name**: a load whose publish pushes a generation out of the window of 12, which it deletes by name. The
  delete is free, and the load makes no listing.
- **listing**: the load at generation 16, which lists the segment once, and deletes by name as well.

**Measured**, each kind's requests (every load of a kind made the same) and the median of its time:

| kind of load | loads | requests | each | per million | median time |
|---|---|---|---|---|---|
| first | 1 | 2 PUT + 3 GET | $0.0000112 | **$11.20** | 81.73 ms |
| reload | 12 | 2 PUT + 2 GET | $0.0000108 | **$10.80** | 109.47 ms |
| by name | 4 | 2 PUT + 4 GET + 1 delete | $0.0000116 | **$11.60** | 176.94 ms |
| listing | 1 | 3 PUT-class + 5 GET + 1 delete | $0.0000170 | **$17.00** | 220.58 ms |

- The requests are **measured**, and the price is **derived**: the counts at the list prices, with the delete free.
  A load that deletes by name made 7 requests, 2 PUT-class, 4 GET-class and a delete; the load that lists made 9.
  All 18 loads made the requests of their kind, and none was discarded: the stage made 37 PUT-class requests and 48
  GET-class requests, the counts the harness expected.
- **Derived**, over a cycle of 16 loads of which 15 delete by name and one lists, the average is $11.94 per million
  (15 loads at $11.60 and one at $17.00, divided by 16). It is arithmetic over two measured kinds and assumes the
  cadence of one listing in 16 generations; the run listed once.
- A kind with one load has a median of one sample: the first load's 81.73 ms and the listing's 220.58 ms are single
  loads, and the reload's and by-name medians are of 12 and 4. The times do not follow the request counts
  closely: the first load made more requests than a reload and was quicker, and the run does not say why.
- Each load wrote a very small object, so these loads show the requests of a refresh load, not the time to move bytes.

## What this run does not establish

- **Other shapes.** It measured two operands at one overlap, plus the sweep to 2,000 shared chunks, all of which lie
  together. Not more operands, not other combine shapes, not the `*Into` verbs, and not `iterate`, which the harness
  does not time: its request count stays expected.
- **Chunks that lie far apart.** The spread layout joined into one range as well. A layout whose shared chunks are
  more than a MiB apart in an object makes more than one range, and this run did not measure one.
- **Bytes outside the region.** Inside the region S3 does not bill bytes read. The spread layout read a range of
  1,022,196 bytes, against the packed layout's 51,600; what that costs across regions or to the internet is not measured.
- **A steady load at other `keep` values.** It ran at `keep: 12`. The requests of a load at a `keep` of 1, or of 64, or of any other window were not measured, nor were those of a segment whose row records no list.
- **More than one listing, or one first load.** The stage ran 18 loads: one first load, one load that lists, 4 that delete by name and 12 reloads. The $11.94 average assumes a listing every 16 generations and is not a measured rate; the run saw one listing, and its figure for the listing's price is that one load's.
- **A steady multipart load, an encrypted segment, or another cloud's load.** The stage loaded a very small object on S3. Azure Blob makes two requests for a tail read, and Google Cloud Storage and Azure Blob were not run.
- **A load that loses a race.** Every load of the stage was the only writer of its segment.
- **Lambda.** A function's cold start and initialisation are a separate figure, and need a run from inside one.
- **Other clouds.** It ran on S3. Google Cloud Storage and Azure Blob Storage have no in-region run.
- **Comparison with other runs' latencies.** Each run is one CloudShell session on one day, and latencies from runs in different sessions are not comparable. The request counts are what repeats from run to run.
- **One client, one moment.** One CloudShell session on one day. S3's own time to answer varies, and the 25 to 30 ms
  round is this run's, not a guarantee.
- **A small sample.** The `andNot` and the cold counts are 10 samples each, the sweep's row for 2,000 shared chunks 5.
- **Why the rounds sit above the model.** The run did not vary the socket count, and no stage held more in flight
  than the client's sockets, so it does not show what part of the gap anything accounts for.
- **The invoice.** These are list prices applied to request counts metered at the SDK, not AWS's bill.
- **Other regions and larger segments.** A round from another region, or a segment whose index outgrows the tail
  read, would differ.

## Where this run sits

On the [roadmap](../../docs/ROADMAP.md#on-the-way-to-10), `1.0` waits on real-cloud calibration, among other things.
This run measures the single-bucket topology's latency on the engine that ships in `0.17.0`, and measures a steady `store.load()` for the first time. The benchmarks page
keeps the one list of [what is still owed](../../docs/benchmarks.md#what-is-still-owed).
