# Calibration run `2026-10-05-50b5d`

**One real run against Amazon S3 in `us-east-1`, from AWS CloudShell in the same region, on 2026-10-05 (UTC), against
the published `0.16.0`.** It is the fourth complete in-region run, and the first of the engine whose registry write
takes the row it already holds, which a load's first publish makes in one GET fewer. Its client sat 4 ms from S3, so its latencies and load rates are the library's,
not a network's. It measures load throughput, cold intersect latency, point reads and `andNot` on the single-bucket
design, and the bill for all of it. The earlier runs, [`2026-10-03-e13c7`](2026-10-03-e13c7.md),
[`2026-10-04-73668`](2026-10-04-73668.md) and [`2026-10-04-f3599`](2026-10-04-f3599.md), measured earlier releases and
stay as the record of them.

The evidence is [`2026-10-05-50b5d.json`](2026-10-05-50b5d.json), the results file the harness wrote, unedited. Every
dollar amount, percentage, duration, byte size and ratio on this page, and every number written before the request,
chunk, id or load it counts, is checked against the evidence by
[`tests/docs/calibration-reports.test.ts`](../../tests/docs/calibration-reports.test.ts). So are the bill and the
request ledger, row by row. [`bench/README.md`](../README.md#real-cloud-calibration) describes the harness, and
[`docs/benchmarks.md`](../../docs/benchmarks.md#real-cloud-calibration--aws) is where these figures are published.

Every figure below is one of three kinds, and the text labels each one where it is first stated:

- **measured**: read straight from the evidence file;
- **derived**: measured request counts multiplied by the list prices in the library's default pricing profile
  (`aws-us-east-1-ondemand`: $0.40 per million GETs, $5 per million PUT-class requests, $0.023 per GiB-month), or
  other arithmetic over measured figures;
- **expected**: what the library's code and its tests predict, not something this run counted.

Four terms recur:

- a **cold** intersect starts with nothing cached: a fresh store, which has read nothing yet;
- a **tail read** is a reader's first read of an object: its last 256 KiB, which holds the footer and the index;
- a **range read** is one request for a stretch of an object's bytes, which holds every shared chunk that lies within
  256 KiB of the one before it, up to 1 MiB;
- **PUT-class** requests are the ones S3 bills at the PUT rate: PUTs, a multipart upload's create, part and complete
  requests, and listings.

Run in the region, with no retry and no discarded sample, every stage exact and every request count equal to its

   127.81 ms). It made 6 GETs, the count the code predicts: a pointer and a tail read for each operand, and one range
   read each for the 100 shared chunks. 40 of 40 intersects returned the planned ids (**measured**).

   in flight and a peak of 11 (**measured**).
3. **Load throughput: 3.28 million ids a second single-part, 10.57 million multipart**, from the median
   `store.load()` of a 1.05 MB and a 12.6 MB segment (**measured**).

   request, 27.15 ms; once cached, a read is microseconds (**measured**).
5. **The bill: 6 GETs, $0.0000024 a cold intersect, $2.40 per million** (**derived**). A segment's first single-part

## Chunk-skipping on real S3

```
 segment A: each square is 20 chunks
 ■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 □□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 ■ read as ONE range      the 100 shared chunks, 5.0% of the chunks
 □ never requested      1,899 chunks · 95.0%
```

**Measured.** An intersect read each operand's 100 shared chunks as a single range request, and never requested the
other 1,899 chunks, 95.0% of the chunks. It knew which chunks could contribute from the two indexes alone, as the
earlier runs' did. It fetched 100 of 1,999 chunks from each segment, 5.0% of them by count. The 100 chunks are not
each a request, because they lie together and one range holds them all.

The 5.0% counts chunks. Counted in bytes, the chunk payload fetched is 4.9% of the two objects, a slightly smaller
share, because an object also holds its index and footer, and the 256 KiB tail read at the end of each one is
fixed.

## 1. Loading data

```
 a 1.05 MB segment, one PUT                   a 12.6 MB segment, multipart
   store.load()  =  2 PUT-class + 3 GET         store.load()  =  5 PUT-class + 3 GET
```

**Measured**, the median of each kind of load, timed over the whole `store.load()` call:

| | single-part | multipart |
|---|---|---|
| loads | 20 | 5 |
| the object | 1,052,088 bytes | 12,622,960 bytes |
| ids a second | 3,278,616 | 10,568,102 |
| bytes a second | 6,900,490 | 10,601,958 |
| requests a load | 2 PUT-class + 3 GET | 5 PUT-class + 3 GET |

- A single-part load of 500,000 ids took about 153 ms, and a multipart load of 12,582,912 ids about 1.19 s
  (**derived**, from the rates).
- Each load uploaded 260 to 263 bytes more than its object: the pointer's body, which is not part of the object.
  The harness records the two apart, as `medianUploadBytes` and `medianObjectBytes`; every size on this page is the
  object's.
- A load's rate divides its bytes by the whole call. That includes building the object, then the loader's reads and
  writes of the pointer, one after another. A multipart load spreads the same sequence of waits over a larger object,
  and over parts uploaded together, so its byte rate is higher.
- The run's 25 loads made 65 PUT-class requests in all. They also made 75 GETs. The harness expected exactly those counts, and every load was a segment's first, so this run measures that load's requests: 2 PUT-class + 3 GET single-part and 5 PUT-class + 3 GET multipart. It does not measure a reload of a segment or a load that finds earlier generations to collect.

## 2. Cold intersect latency

```
 A ∩ B    two segments of 500,000 ids · 1,999 chunks each · 100 chunks in common

   pointer   A ── 1 GET ─────┐
             B ── 1 GET ─────┤
   tail      A ── 1 GET ─────┤   the last 256 KiB of each object
             B ── 1 GET ─────┤
   chunks    A ── 1 GET ─────┤   one range: the 100 shared chunks
             B ── 1 GET ─────┘
                             ──────────
                             6 GETs  →  $0.0000024 an intersect
```

**Measured**, 40 cold intersects each:

| layout | p50 | p95 | p99 | GETs | rounds |
|---|---|---|---|---|---|
| the shared chunks packed together | 92.63 ms | 116.50 ms | 127.81 ms | 6 | 3.7 |
| the shared chunks spread across the segment | 104.00 ms | 159.42 ms | 221.32 ms | 6 | 3.9 |

- Every intersect returned exactly the planned ids, checked by count and by sum, and read one range and one tail
  per operand. The median made 6 GETs: 2 pointer reads, 2 tail reads and 2 range reads. Each pointer was read
  once, because an intersect finished well inside the 2 s pointer refresh. Nothing was off the expected count, and
  the harness turned the pointer refresh off for the timed intersects (`cache.genTtlMs: 0`), so the count does not
  move with the network.
- With 40 samples, the p99 is the slowest intersect and the p95 the second slowest.
- The spread layout also took 6 GETs: its shared chunks lie across each object, and the engine joined them into one
  range anyway. Each range read returned 1,022,196 bytes of an operand (**derived**: the stage's range bytes over its range
  requests), because the bytes between the chunks come with them. The packed layout's range returned 51,600 bytes.
- A cold intersect is the worst case for this design: nothing cached, every byte from S3.

### Rounds

The engine reads each operand's pointer, then its tail, both operands at once. It then reads the shared chunks of
each operand as one range, both operands at once. That makes a model of 3 requests in line, each waiting for the one
before (**expected**, from the engine's code, the rounds model, which assumes no limit on open sockets). The run
measured 3.7 rounds for the packed layout and 3.9 for the spread one: the median's mean in-flight requests, divided
into its total request time, so a round is a request's duration averaged over everything in flight (the harness's own
figure; the model is not tuned to it). The measured depth is above the rounds model's: 3.7 against 3, and the spread
layout's 3.9.

**The measured rounds are above the rounds model, and the run does not say why.** The client had 128 sockets, and
the model assumes no socket limit. The packed intersect's median peaked at 2 in flight and held a mean of 1.6 (the
spread layout's, 1.5), so a socket limit did not bind. The gap is a finding and is not tuned away. The run did not vary
the socket count.

**A GET round is about 25 to 28 ms in this run** (**derived**: p50 ÷ measured rounds, 92.63 ms ÷ 3.7 = 25.3 ms, and
26.5 ms for the spread layout; the sweep below gives 25.1 and 28.2, and the `andNot` 29.0). That is more than the
round-trip floor of 4.32 ms. The run does not say why: S3's own time to first byte and the client's connection
handling are both candidates, and so is the time to read a range of up to 1 MiB.

## 3. How a cold intersect grows with the overlap

The same intersect at more shared chunks, `k`, each on a fresh store (**measured**):

| shared chunks | intersects | p50 | p95 | GETs | rounds | model |
|---|---|---|---|---|---|---|
| 1,000 | 10 | 152.02 ms | 168.63 ms | 6 | 6.0 | 3 |
| 2,000 | 5 | 218.45 ms | 258.72 ms | 6 | 7.7 | 3 |

- Doubling `k` did not change the GETs: 6 at both. The shared chunks lie together, so each operand's are one range
  however many there are. The p50 went from 152.02 ms to 218.45 ms, 1.44 times (**derived**), for twice the chunks:
  the requests stayed the same and each carried more bytes.
- With 10 and 5 samples, the p95 is the slowest or the second slowest intersect and says little by itself.
- The rounds again run above the rounds model's: 6.0 against 3 and 7.7 against 3. At these in-flight depths, 1.0 and
  0.8 on average, the run does not say why.

## 4. Warm intersect, point reads and `andNot`

**Warm intersect** (**measured**, 40 intersects on a store that had read both segments already): p50 3.94 ms, p95
6.54 ms and p99 6.83 ms, with no request at all. Answering from memory is a few milliseconds; the work is merging
the chunks.

**Point reads** (**measured**, 10 segments):

| read | requests | p50 | p95 |
|---|---|---|---|
| `count()`, cold | 1 | 28.17 ms | 52.24 ms |
| `has()`, opening the segment | 1 | 30.56 ms | 38.98 ms |
| `has()`, on an open segment, first read of a chunk | 1 | 27.15 ms | 40.25 ms |
| `has()`, first read of an id on a store with the pointer refresh off | 3 | 80.43 ms | 101.96 ms |
| `count()`, warm | 0 | 0.0031 ms | 0.0051 ms |
| `has()`, warm | 0 | 0.0054 ms | 0.0069 ms |

- A cold `count()` is one request: the cardinality is in the pointer's row, so it opens nothing. Its 28.17 ms is one
  GET round.
- A `has()` on an open segment is one chunk GET, one round. The first read on a store that had to read the pointer,
  the tail and then the chunk is three requests, three rounds, 80.43 ms.
- A warm read never leaves memory: under 10 microseconds at the median.

**`andNot`** (**measured**, 10 calls, each of a 1,999-chunk segment with 10 excludes): p50 255.60 ms, p95
345.28 ms and p99 345.28 ms. Each call made 33 GETs: 11 range reads, 11 tail reads and 11 pointer reads, with a mean
in flight of 3.8 and up to 11 at the peak. Each operand, the include and the ten excludes, had its pointer and
tail read and its chunks read as one range; the rounds were 8.8.

## What this run does not establish

- **Other shapes.** It measured two operands at one overlap, plus the sweep to 2,000 shared chunks, all of which lie
  together. Not more operands, not other combine shapes, not the `*Into` verbs, and not `iterate`, which the harness
  does not time: its request count stays expected.
- **Chunks that lie far apart.** The spread layout joined into one range as well. A layout whose shared chunks are
  more than a MiB apart in an object makes more than one range, and this run did not measure one.
- **Bytes outside the region.** Inside the region S3 does not bill bytes read. The spread layout read a range of
  1,022,196 bytes, against the packed layout's 51,600; what that costs across regions or to the internet is not measured.
- **Lambda.** A function's cold start and initialisation are a separate figure, and need a run from inside one.
- **Other clouds.** It ran on S3. Google Cloud Storage and Azure Blob Storage have no in-region run.
- **One client, one moment.** One CloudShell session on one day. S3's own time to answer varies, and the 25 to 28 ms
  round is this run's, not a guarantee.
- **A small sample.** The `andNot` and the cold counts are 10 samples each, the sweep's row for 2,000 shared chunks 5.
- **Why the rounds sit above the model.** The run did not vary the socket count, and no stage held more in flight
  than the client's sockets, so it does not show what part of the gap anything accounts for.
- **The invoice.** These are list prices applied to request counts metered at the SDK, not AWS's bill.
- **Other regions and larger segments.** A round from another region, or a segment whose index outgrows the tail
  read, would differ.
