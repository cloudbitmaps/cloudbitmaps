# Calibration run `2026-10-04-73668`

**One real run against Amazon S3 in `us-east-1`, from AWS CloudShell in the same region, on 2026-10-04 (UTC), against
the published `0.13.0`.** It is the second complete in-region run, and the first of the engine that opens a combine's
window 8 keys wide and widens it to 32. Its client sat 5 ms from S3, so its latencies and load rates are the
library's, not a network's. It measures load throughput, cold intersect latency, point reads and `andNot` on the
single-bucket design, and the bill for all of it. It measures what [the previous run,
`2026-10-03-e13c7`](2026-10-03-e13c7.md), made on `0.12.0` with a window of 8, could only model.

The evidence is [`2026-10-04-73668.json`](2026-10-04-73668.json), the results file the harness wrote, unedited. Every
dollar amount, percentage, duration, byte size and ratio on this page, and every number written before the request,
chunk, id or load it counts, is checked against the evidence by
[`tests/docs/calibration-reports.test.ts`](../../tests/docs/calibration-reports.test.ts). So are the bill and the
request ledger, row by row. [`bench/README.md`](../README.md#real-cloud-calibration) describes the harness, and
[`docs/benchmarks.md`](../../docs/benchmarks.md#real-cloud-calibration--aws) is where these figures are published.

Every figure below is one of three kinds, and the text labels each one where it is first stated:

- **measured**: read straight from the evidence file;
- **derived**: measured request counts multiplied by the list prices in the library's default pricing profile
  (`aws-us-east-1-ondemand`: $0.40 per million GETs, $5 per million PUT-class requests, $0.023 per GiB-month), or
  other arithmetic over measured figures;
- **expected**: what the library's code and its tests predict, not something this run counted.

Three terms recur:

- a **cold** intersect starts with nothing cached: a fresh store, which has read nothing yet;
- a **tail read** is a reader's first read of an object: its last 256 KiB, which holds the footer and the index;
- **PUT-class** requests are the ones S3 bills at the PUT rate: PUTs, a multipart upload's create, part and complete
  requests, and listings.

## At a glance

Run in the region, with no retry and no discarded sample, every stage exact and every request count equal to its
expectation:

1. **Cold intersect, 100 of 1,999 chunks shared: 290 ms at the median** (p50 290.06 ms, p95 416.22 ms, p99 588.99 ms).
   It made 204 GETs, the count the code predicts, and 40 of 40 intersects returned the planned ids (**measured**).
2. **`andNot` of a 1,999-chunk segment against ten excludes: 3,335.85 ms at the median**, with 3,021 GETs, a mean of
   80.6 in flight and a peak of 352 (**measured**).
3. **Load throughput: 2.42 million ids a second single-part, 10.4 million multipart**, from the median
   `store.load()` of a 1.05 MB and a 12.6 MB segment (**measured**).
4. **Point reads: a cold `count()` is one request, 27.82 ms at the median.** A `has()` on an open segment is one
   request, 25.94 ms; once cached, a read is microseconds (**measured**).
5. **The bill: 204 GETs, $0.0000816 a cold intersect, $81.60 per million** (**derived**). A single-part
   `store.load()` is 2 PUT + 4 GET, $11.60 per million (**measured** requests, **derived** price). The run's
   requests cost $0.037635 in all (**derived**), the same requests as the previous run's, to the request.
6. **The rounds sit above the rounds model.** They are a fifth to a half above it. The client had 50 sockets, the SDK
   default. Only the `andNot` held more requests in flight than that (mean 80.6, peak 352); the cold intersect and

## Chunk-skipping on real S3

```
 segment A: each square is 20 chunks
 ■■■■■□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 □□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□□
 ■ fetched      100 chunks ·  5.0%
 □ skipped    1,899 chunks · 95.0%   never requested
```

**Measured.** An intersect fetched 100 of 1,999 chunks from each segment, 5.0% of them by count, and never requested
the other 1,899 chunks, 95.0% of the chunks. It knew which chunks could contribute from the two indexes alone, as it
did on the two earlier runs.

The 5.0% counts chunks. Counted in bytes, the chunk payload fetched is 4.9% of the two objects, a slightly smaller
share, because an object also holds its index and footer, and the 256 KiB tail read at the end of each one is
fixed.

## 1. Loading data

```
 a 1.05 MB segment, one PUT                   a 12.6 MB segment, multipart
   store.load()  =  2 PUT-class + 4 GET         store.load()  =  5 PUT-class + 4 GET
```

**Measured**, the median of each kind of load, timed over the whole `store.load()` call:

| | single-part | multipart |
|---|---|---|
| loads | 20 | 5 |
| the object | 1,052,088 bytes | 12,622,960 bytes |
| ids a second | 2,423,349 | 10,399,338 |
| bytes a second | 5,100,414 | 10,432,654 |
| requests a load | 2 PUT-class + 4 GET | 5 PUT-class + 4 GET |

- A single-part load of 500,000 ids took about 206 ms, and a multipart load of 12,582,912 ids about 1.21 s
  (**derived**, from the rates).
- Each load uploaded 260 to 263 bytes more than its object: the pointer's body, which is not part of the object.
  The harness records the two apart, as `medianUploadBytes` and `medianObjectBytes`; every size on this page is the
  object's.
- A load's rate divides its bytes by the whole call. That includes building the object, then the loader's reads and
  writes of the pointer, one after another. A multipart load spreads the same sequence of waits over a larger object,
  and over parts uploaded together, so its byte rate is higher.
- The run's 25 loads made 65 PUT-class requests in all. They also made 100 GETs. The harness expected exactly those counts.
- The single-part rate, 2.42 million ids a second, is below the previous run's (its report has it). `0.13.0` made no change
  to the load path (from the code, not from this run). One run of each does not say why the rate differs, and this
  report does not guess.

## 2. Cold intersect latency

```
 A ∩ B    two segments of 500,000 ids · 1,999 chunks each · 100 chunks in common

   pointer   A ── 1 GET ─────┐
             B ── 1 GET ─────┤
   tail      A ── 1 GET ─────┤   the last 256 KiB of each object
             B ── 1 GET ─────┤
   chunks    A ── 100 GETs ──┤   only the chunks both segments hold
             B ── 100 GETs ──┘
                             ──────────
                             204 GETs  →  $0.0000816 an intersect
```

**Measured**, 40 cold intersects each:

| layout | p50 | p95 | p99 | GETs | rounds |
|---|---|---|---|---|---|
| the shared chunks packed together | 290.06 ms | 416.22 ms | 588.99 ms | 204 | 7.1 |
| the shared chunks spread across the segment | 269.45 ms | 471.55 ms | 473.32 ms | 204 | 7.5 |

- Every intersect returned exactly the planned ids, checked by count and by sum, and read 100 chunks and one tail
  per operand. The median made 204 GETs: 2 pointer reads, 2 tail reads and 200 chunk reads. Each pointer was read
  once, because an intersect finished well inside the 2 s pointer refresh. Nothing was off the expected count, and
  the harness turned the pointer refresh off for the timed intersects (`cache.genTtlMs: 0`), so the count does not
  move with the network.
- With 40 samples, the p99 is the slowest intersect and the p95 the second slowest.
- Packing the shared chunks or spreading them changes the tail, not the median: the spread layout's median is
  269.45 ms against 290.06 ms, within the run's own spread.
- A cold intersect is the worst case for this design: nothing cached, every byte from S3.

### Rounds

The engine reads each operand's pointer, then its tail, both operands at once. It then opens its window 8
keys wide and widens it to 32 as it takes keys, reading each chunk from both operands at once, so 100 shared chunks
take about 4 rounds of chunks after the 2 of index reads. That makes a model of 6 requests in line, each waiting for
the one before (**expected**, from the engine's code, the rounds model, which assumes no limit on open sockets). The run measured 7.1
rounds for the packed layout and 7.5 for the spread one: the median's mean in-flight requests, divided into its total
request time, so a round is a request's duration averaged over everything in flight (the harness's own figure; the
model is not tuned to it). The measured depth is above the rounds model's: 7.1 against 6, and the spread layout's 7.5.

**The measured rounds are above the rounds model, and the run does not say why.** The client had 50 sockets, and the
model assumes no socket limit. The packed intersect's median peaked at 64 in flight but held a mean of 29.1 (the
spread layout's, 27.4); the sweeps held a mean of 41.3 and 43.4, under 50 too. Only the `andNot` held more in flight
than the client has sockets, a mean of 80.6 and a stage-median peak of 352 (the run-wide peak was 351). The gap is a
finding and is not tuned away. The run did not vary the socket count, so it does not say what part of the gap is
socket wait, and no figure is claimed for any other count.

**A GET round is about 36 to 41 ms in this run** (**derived**: p50 ÷ measured rounds, 290.06 ms ÷ 7.1 = 40.7 ms, and
35.9 ms for the spread layout; the sweep below gives 36.0 and 35.6, and the `andNot` 88.8). That is more than the
round-trip floor of 5.01 ms, and longer in the stages with more requests open together. The run does not say why:
S3's own time to first byte, the client's connection handling and a wait for a socket are all candidates.

## 3. How a cold intersect grows with the overlap

The same intersect at more shared chunks, `k`, each on a fresh store (**measured**):

| shared chunks | intersects | p50 | p95 | GETs | rounds | model |
|---|---|---|---|---|---|---|
| 1,000 | 10 | 1,808.80 ms | 3,143.44 ms | 2,004 | 50.2 | 34 |
| 2,000 | 5 | 3,291.35 ms | 3,346.52 ms | 4,004 | 92.4 | 66 |

- Doubling `k` doubled the GETs, 2,004 to 4,004, and took the p50 from 1.81 s to 3.29 s, 1.82 times: near-linear
  scaling (**derived**). A cold intersect's latency grows with the overlap, because each shared chunk is a request.
- The GET count is the cold-intersect formula, 4 + 2k, the same one that gives 204 at 100 shared chunks.
- With 10 and 5 samples, the p95 is the slowest or the second slowest intersect and says little by itself.
- The rounds again run above the rounds model's: 50.2 against 34 and 92.4 against 66, a fifth to a half more, as at 100
  shared chunks.

## 4. Warm intersect, point reads and `andNot`

**Warm intersect** (**measured**, 40 intersects on a store that had read both segments already): p50 4.05 ms, p95
7.02 ms and p99 12.36 ms, with no request at all. Answering from memory is a few milliseconds; the work is merging
the chunks.

**Point reads** (**measured**, 10 segments):

| read | requests | p50 | p95 |
|---|---|---|---|
| `count()`, cold | 1 | 27.82 ms | 35.11 ms |
| `has()`, opening the segment | 1 | 31.24 ms | 37.05 ms |
| `has()`, on an open segment, first read of a chunk | 1 | 25.94 ms | 32.91 ms |
| `has()`, first read of an id on a store with the pointer refresh off | 3 | 80.31 ms | 98.44 ms |
| `count()`, warm | 0 | 0.0032 ms | 0.0051 ms |
| `has()`, warm | 0 | 0.0047 ms | 0.0070 ms |

- A cold `count()` is one request: the cardinality is in the pointer's row, so it opens nothing. Its 27.82 ms is one
  GET round.
- A `has()` on an open segment is one chunk GET, one round. The first read on a store that had to read the pointer,
  the tail and then the chunk is three requests, three rounds, 80.31 ms.
- A warm read never leaves memory: under 10 microseconds at the median.

**`andNot`** (**measured**, 10 calls, each of a 1,999-chunk segment with 10 excludes): p50 3,335.85 ms, p95
3,879.78 ms and p99 3,879.78 ms. Each call made 3,021 GETs: 2,999 chunk reads, 11 tail reads and 11 pointer reads,
with a mean in flight of 80.6 and up to 352 at the peak. The engine reads every chunk of the including
segment, so this is a large-overlap shape; the rounds were 37.5. The 352 is the stage's median of its calls' peaks. Both it and the mean of 80.6 are above
the client's 50 sockets: this is the one stage that held more in flight than that.

## What this run shows against the previous one

The previous run, [`2026-10-03-e13c7`](2026-10-03-e13c7.md), was made on `0.12.0`, whose combine kept a fixed window of
8 keys and read an exclude's chunk after the include's. This run is the same harness and the same workload on
`0.13.0`. Both are one run, from one CloudShell each, so a difference is the size of what one run of each can show.

- **The same requests, in fewer rounds.** Every request count is the previous run's, to the request, and the bill is
  the same $0.037635. The window changed how many requests are open together, not how many are made. The cold
  intersect, the sweeps and the `andNot` each took fewer rounds and a shorter median than the previous run's, and
  the `andNot` took the largest share off. The figures for both runs are in [the previous run's report](2026-10-03-e13c7.md) and this one.
- **Not as few rounds as the rounds model said.** The run's rounds are a fifth to a half above the model's, which assumes no
  socket limit. This run's client had 50 sockets, and only the `andNot` held more than that in flight (mean 80.6, peak
  352). The run did not vary the socket count, so it does not say what part of the gap is socket wait. Raising the built client's socket
  count is a separate, open change; this run does not measure it, and no figure here is claimed for it.
- **Point reads are where they were.** A cold `count()` and a `has()` on an open segment are one request each, about
  one round, and the warm intersect is a few milliseconds, all as in the previous run.

## What this run does not establish

- **Other shapes.** It measured two operands at one overlap, plus the sweep to 2,000 shared chunks. Not more
  operands, not other combine shapes, not the `*Into` verbs.
- **Lambda.** A function's cold start and initialisation are a separate figure, and need a run from inside one.
- **Other clouds.** It ran on S3. Google Cloud Storage and Azure Blob Storage have no in-region run.
- **One client, one moment.** One CloudShell session on one day. S3's own time to answer varies, and the 36 to 41 ms
  round is this run's, not a guarantee.
- **A small sample.** The `andNot` and the cold counts are 10 samples each, the sweep's row for 2,000 shared chunks 5. The
  difference from the previous run is one run against one run.
- **What a wider client does.** The run used the SDK's 50 sockets. It shows the `andNot` above that in flight and
  the rounds above the rounds model; it does not show what a client with more sockets would measure.
- **The invoice.** These are list prices applied to request counts metered at the SDK, not AWS's bill.
- **Other regions and larger segments.** A round from another region, or a segment whose index outgrows the tail
  read, would differ.
