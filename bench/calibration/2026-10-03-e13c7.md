# Calibration run `2026-10-03-e13c7`

**One real run against Amazon S3 in `us-east-1`, from AWS CloudShell in the same region, on 2026-10-03 (UTC).** It is
the first complete in-region run of the loaded store's calibration harness: its client sat 5 ms from S3, so its
latencies and load rates are the library's, not a network's. It measures load throughput, cold intersect latency,
point reads and `andNot` on the single-bucket design, and the bill for all of it.

The evidence is [`2026-10-03-e13c7.json`](2026-10-03-e13c7.json), the results file the harness wrote, unedited. Every
dollar amount, percentage, duration, byte size and ratio on this page, and every number written before the request,
chunk, id or load it counts, is checked against the evidence by
[`tests/docs/calibration-reports.test.ts`](../../tests/docs/calibration-reports.test.ts). So are the bill and the
request ledger, row by row. [`bench/README.md`](../README.md#real-cloud-calibration) describes the harness, and
[`docs/benchmarks.md`](../../docs/benchmarks.md#real-cloud-calibration--aws) is where these figures are published.

Every figure below is one of three kinds, and the text labels each one where it is first stated:

- **measured**: read straight from the evidence file;
- **derived**: measured request counts multiplied by the list prices in the library's default pricing profile
  (`aws-us-east-1-ondemand`: $0.40 per million GETs, $5 per million PUT-class requests, $0.023 per GiB-month), or
  other arithmetic over measured figures;
- **expected**: what the library's code and its tests predict, not something this run counted.

Three terms recur:

- a **cold** intersect starts with nothing cached: a fresh store, which has read nothing yet;
- a **tail read** is a reader's first read of an object: its last 256 KiB, which holds the footer and the index;
- **PUT-class** requests are the ones S3 bills at the PUT rate: PUTs, a multipart upload's create, part and complete
  requests, and listings.

## At a glance

Run in the region, with no retry and no discarded sample, every stage exact and every request count equal to its
expectation:

1. **Cold intersect, 100 of 1,999 chunks shared: 493 ms at the median** (p50 492.69 ms, p95 559.30 ms, p99 571.10 ms).
   It made 204 GETs, the count the code predicts, and 40 of 40 intersects returned the planned ids (**measured**).
2. **Load throughput: 2.86 million ids a second single-part, 11.3 million multipart**, from the median
   `store.load()` of a 1.05 MB and a 12.6 MB segment (**measured**).
3. **Point reads: a cold `count()` is one request, 27.48 ms at the median.** A `has()` on an open segment is one
   request, 25.60 ms; once cached, a read is microseconds (**measured**).
4. **The bill: 204 GETs, $0.0000816 a cold intersect, $81.60 per million** (**derived**). A single-part
   `store.load()` is 2 PUT + 4 GET, $11.60 per million (**measured** requests, **derived** price). The run's
   requests cost $0.037635 in all (**derived**).

## 1. Loading data

```
 a 1.05 MB segment, one PUT                   a 12.6 MB segment, multipart
   store.load()  =  2 PUT-class + 4 GET         store.load()  =  5 PUT-class + 4 GET
```

**Measured**, the median of each kind of load, timed over the whole `store.load()` call:

| | single-part | multipart |
|---|---|---|
| loads | 20 | 5 |
| the object | 1,052,088 bytes | 12,622,960 bytes |
| ids a second | 2,860,516 | 11,303,057 |
| bytes a second | 6,020,505 | 11,339,268 |
| requests a load | 2 PUT-class + 4 GET | 5 PUT-class + 4 GET |

- A single-part load of 500,000 ids took about 175 ms, and a multipart load of 12,582,912 ids about 1.11 s
  (**derived**, from the rates).
- Each load uploaded 260 to 263 bytes more than its object: the pointer's body, which is not part of the object.
  The harness records the two apart, as `medianUploadBytes` and `medianObjectBytes`; every size on this page is the
  object's.
- A load's rate divides its bytes by the whole call. That includes building the object, then the loader's reads and
  writes of the pointer, one after another. A multipart load spreads the same sequence of waits over a larger object,
  and over parts uploaded together, so its byte rate is higher.
- The run's 25 loads made 65 PUT-class and 100 GET requests, and the harness expected exactly those.

## 2. Cold intersect latency

```
 A ∩ B    two segments of 500,000 ids · 1,999 chunks each · 100 chunks in common

   pointer   A ── 1 GET ─────┐
             B ── 1 GET ─────┤
   tail      A ── 1 GET ─────┤   the last 256 KiB of each object
             B ── 1 GET ─────┤
   chunks    A ── 100 GETs ──┤   only the chunks both segments hold
             B ── 100 GETs ──┘
                             ──────────
                             204 GETs  →  $0.0000816 an intersect
```

**Measured**, 40 cold intersects each:

| layout | p50 | p95 | p99 | GETs | rounds |
|---|---|---|---|---|---|
| the shared chunks packed together | 492.69 ms | 559.30 ms | 571.10 ms | 204 | 18.3 |
| the shared chunks spread across the segment | 493.19 ms | 716.10 ms | 725.78 ms | 204 | 18.5 |

- Every intersect returned exactly the planned ids, checked by count and by sum, and read 100 chunks and one tail
  per operand. The median made 204 GETs: 2 pointer reads, 2 tail reads and 200 chunk reads. Each pointer was read
  once, because an intersect finished well inside the 2 s pointer refresh. Nothing was off the expected count, and
  the harness turned the pointer refresh off for the timed intersects (`cache.genTtlMs: 0`), so the count does not
  move with the network.
- With 40 samples, the p99 is the slowest intersect and the p95 the second slowest.
- Packing the shared chunks or spreading them changes the tail, not the median: the spread layout's p95 is 716.10 ms
  against 559.30 ms.
- A cold intersect is the worst case for this design: nothing cached, every byte from S3.

**Rounds.** The engine reads each operand's pointer, then its tail, both operands at once. It then keeps 8 shared
chunks in flight, reading each from both operands at once, so 100 shared chunks take about 13 rounds. That makes a
model of 15 requests in line, each waiting for the one before (**expected**, from the engine's code). The run
measured 18.3 rounds for the packed layout and 18.5 for the spread one: the median's mean in-flight requests,
divided into its total request time, so a round is a request's duration averaged over everything in flight (the
harness's own figure; the model is not tuned to it). The measured depth is above the model's.

**A GET round is about 26 to 27 ms in-region** (**derived**: p50 ÷ measured rounds, 492.69 ms ÷ 18.3 = 26.9 ms, and
26.6 ms for the spread layout; the sweep below gives 26.4 and 26.7). That is about five times the 5.07 ms round-trip
floor. The run does not say where the rest goes: S3's own time to first byte, and the client's connection handling,
are both candidates. What it does show is that the figure is stable across the layouts and sizes this run covered.

## 3. How a cold intersect grows with the overlap

The same intersect at more shared chunks, `k`, each on a fresh store (**measured**):

| shared chunks | intersects | p50 | p95 | GETs | rounds | model |
|---|---|---|---|---|---|---|
| 1,000 | 10 | 4,238.82 ms | 5,765.95 ms | 2,004 | 160.4 | 127 |
| 2,000 | 5 | 8,658.44 ms | 9,046.63 ms | 4,004 | 324.0 | 252 |

- Doubling `k` doubled the GETs, 2,004 to 4,004, and took the p50 from 4.24 s to 8.66 s, 2.04 times: near-linear
  scaling (**derived**). A cold intersect's latency grows with the overlap, because each shared chunk is a request.
- The GET count is the cold-intersect formula, 4 + 2k, the same one that gives 204 at 100 shared chunks.
- With 10 and 5 samples, the p95 is the slowest or the second slowest intersect and says little by itself.
- The rounds again run above the model's, by about the same fraction as at 100 shared chunks.

## 4. Warm intersect, point reads and `andNot`

**Warm intersect** (**measured**, 40 intersects on a store that had read both segments already): p50 3.96 ms, p95
6.40 ms and p99 7.21 ms, with no request at all. Answering from memory is a few milliseconds; the work is merging
the chunks.

**Point reads** (**measured**, 10 segments):

| read | requests | p50 | p95 |
|---|---|---|---|
| `count()`, cold | 1 | 27.48 ms | 56.34 ms |
| `has()`, opening the segment | 1 | 24.16 ms | 29.04 ms |
| `has()`, on an open segment, first read of a chunk | 1 | 25.60 ms | 32.80 ms |
| `has()`, first read of an id on a store with the pointer refresh off | 3 | 77.63 ms | 91.32 ms |
| `count()`, warm | 0 | 0.0029 ms | 0.0058 ms |
| `has()`, warm | 0 | 0.0045 ms | 0.0068 ms |

- A cold `count()` is one request: the cardinality is in the pointer's row, so it opens nothing. Its 27.48 ms is one
  GET round (**derived**, above).
- A `has()` on an open segment is one chunk GET, one round. The first read on a store that had to read the pointer,
  the tail and then the chunk is three requests, three rounds, 77.63 ms: about 26 ms each.
- A warm read never leaves memory: under 10 microseconds at the median.

**`andNot`** (**measured**, 10 calls, each of a 1,999-chunk segment with 10 excludes): p50 8,687.10 ms, p95
11,146.58 ms and p99 11,146.58 ms. Each call made 3,021 GETs: 2,999 chunk reads, 11 tail reads and 11 pointer reads,
with up to 80 requests in flight at the peak. The engine reads every chunk of the including segment, so this is a
large-overlap shape; the rounds were 303.9.

## What this run does not establish

- **Other shapes.** It measured two operands at one overlap, plus the sweep to 2,000 shared chunks. Not more
  operands, not other combine shapes, not the `*Into` verbs.
- **Lambda.** A function's cold start and initialisation are a separate figure, and need a run from inside one.
- **Other clouds.** It ran on S3. Google Cloud Storage and Azure Blob Storage have no in-region run.
- **One client, one moment.** One CloudShell session on one day. S3's own time to answer varies, and the 26 to 27 ms
  round is this run's, not a guarantee.
- **The invoice.** These are list prices applied to request counts metered at the SDK, not AWS's bill.
- **Other regions and larger segments.** A round from another region, or a segment whose index outgrows the tail
  read, would differ.
